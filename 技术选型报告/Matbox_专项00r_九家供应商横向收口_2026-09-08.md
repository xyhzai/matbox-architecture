## 这份文档是什么，不是什么

**是什么**：九家供应商报告全部 100% 通读 + 数字回查完成后的**跨公司收口**。它回答 00q 里挂着的 B-01 ~ B-08。

**不是什么**：
- **不是总分排名**。九家不在同一层（见 §1），给"谁第一名"是量纲错误。
- **不重复列单家事实**。所有事实在 00q，本文只做跨公司判断，引用时标 `00q §x`。
- **不是 Stage 9 正式开发文档**。这是选型收口，具体模块的正式文档另立。

**证据强度约定**：本文最强的论据类型是**多家独立收敛**——若 N 家互不相干的供应商、从各自不同的业务出发、独立走到同一个设计，那比任何一家的单方意见都硬。每条收敛均标注是哪几家。

**一处已知缺口**：Salesforce 的「家底文档」未纳入（用户 2026-09-08 明确暂不处理）。因此 Salesforce 在"为什么它能做 AI 员工平台"这一层的证据比其余八家薄，涉及该层的判断已单独标注。

## 1｜九家不是同一层：先分层，再谈取舍

这是整份收口最重要的前提。把九家并列打分是错的——它们解决的根本不是同一个问题。

| 层 | 这一层在问什么 | 最值得学的 | 可当 Provider 的 |
|---|---|---|---|
| **客户侧 AI 员工产品形态** | 客户直接对话的 AI 员工长什么样、怎么从对话做到业务结果 | **Fin**（Procedures + Outcome + Escalation + Eval/Release/Monitor） | Fin（闭源 SaaS，且已被 Salesforce 收购） |
| **企业级 AI 员工身份治理** | AI 员工是不是企业身份体系里的一等对象 | **Microsoft**（Entra Agent ID + Agent 365 + Sponsor + Quarantine） | Microsoft（限 M365 重度客户） |
| **岗位 → Agent → Tool → 连接四层拆法** | 一个"岗位员工"内部怎么组织 | **ServiceNow**（四层结构 + T2 SOC 样板 + Control Tower） | ServiceNow（需 Integration Hub 独立订阅） |
| **岗位拆解的粒度** | 一个岗位该拆到多细 | **Salesforce**（Agent Type → Template → Subagent → Action → Reference Action 五级） | Salesforce（含 Fin 后更强） |
| **Connector Factory 源码级实现** | 连接器到底怎么造、怎么可靠地跑 | **Activepieces**（MIT 核心 + Waitpoint + Durable + 三次官方事故复盘） | Activepieces（自托管，但开源版无 Agents/API） |
| **Agent 的工具路由与认证** | 上千个工具怎么让 Agent 找到并安全调用 | **Composio**（Session + Tool Search + Auth Config/Connected Account 分层） | Composio（SDK MIT，Enterprise 可自托管） |
| **全球长尾连接器** | 怎么最快拿到最多的"手" | Zapier（生态生产制度，不是 9,000 这个数） | **Zapier**（Action Runs / MCP / SDK） |
| **企业编排 + Embedded + 私网** | 大企业客户签得下来的那一套 | **Workato**（Environments/RLCM + Embedded + OPA + Enterprise MCP） | Workato（企业价，CN 无 AI/MCP） |
| **RPA / UI 兜底** | 没有 API 的老系统怎么办 | UiPath（Queue/Transaction + Job 状态机 + Robot/Session） | **UiPath**（API-first，RPA last resort） |

> **收口第一条**：Matbox 不是在九家里"选一家"，而是**按层各取所长，且每一层都必须可替换**。

## 2｜多家独立收敛的八条（本文最强论据）

### 收敛 ①：一个 AI 员工 = 多个子 Agent + 专职路由 + HITL —— **4 家独立到达**

| 供应商 | 各自的实现 |
|---|---|
| ServiceNow | T2 SOC = Analysis → Containment → Eradication & Recovery → Review & Closure + 按需 Supporting Agents（`00q §5.2`） |
| Salesforce | Sales Account Management = Record Management / Record Retrieval / **Sales Management Routing（无自己的 Action，专职路由）** / Sales Research（可再委托）/ Slack Operations / Web Retrieval（`00q §6.3`） |
| Microsoft | Connected Agent = 独立 orchestration + tools + knowledge，Parent 整体当一个 Agentic Tool（`00q §2.2`） |
| Workato | Genie 可委派其他 Genie；Recipe 可 `Assign task to genie` 并 pause 等返回（`00q §9.2`） |

> **信号强度：最高。** 四家从 IT 运维、销售 CRM、企业低代码、企业 iPaaS 四个完全不同的业务出发，独立走到同一结构。**Matbox 的 AI 员工不能是"一个大 Prompt"** —— 这条可以直接冻结。
> 特别注意 Salesforce 那个**专职路由 Subagent（自己不带任何 Action）**，是四家里最干净的设计。

### 收敛 ②：确定性流程骨架 + LLM 适应，不是二选一 —— **5 家独立到达**

| 供应商 | 说法 |
|---|---|
| Salesforce | Hybrid Reasoning：Action 分 **Deterministic**（Flow/Apex）与 **Prompt-Based**，可混合（`00q §6.3`） |
| Microsoft | Generative orchestration + Classic/Topic + Agent Flow 并存（`00q §2.2`） |
| Fin | Procedures = Instruction（自然语言）+ Condition（**可 Python**）+ Sub-procedure + HITL（`00q §8.2`） |
| ServiceNow | Blueprint P15–16：概率 AI + 确定性 Workflow，**Workflow 本身作为高层 Tool**，避免 Agent 每次重新编排底层 API 顺序（`00q §5.2`） |
| UiPath | Maestro：BPMN + Agent + Human Task + RPA Workflow 同图（`00q §3.2`） |

> **五家收敛，且各自给了同一句大白话**：能写文章、总结、判断意图的让模型做；**价格、库存、权限、审批、写库、退款、报价计算交给 Flow/API/规则系统**。
> **对 Matbox 的含义**：F-ACTION-001 的 Enforcement Pipeline 方向被五家独立验证。但要补一条 ServiceNow 的洞察——**把"创建采购单""发布商品"这类封成受控 Workflow Tool 给 Agent 用**，而不是让 LLM 每次临时拼 API 顺序。

### 收敛 ③：执行身份 ≠ 员工身份，且必须分 Runtime Profile —— **4 家独立到达**

| 供应商 | 证据 |
|---|---|
| Microsoft | OBO（代表用户）vs App-only（Agent 本身做 token subject）；**Harness 创建后双向不可迁移**（`00q §2.1`） |
| Workato | **verified user access skills 与需 Business approvals 的 Genie，不能用于完全自治的 Assign task to genie 路径**（`00q §9.2`） |
| ServiceNow | Agent 安全控制分"谁能调用这个 Agent"与"Agent 用哪个身份访问数据"；可 Dynamic user 或独立 AI user（`00q §5.2`） |
| Fin | Data Connector 的 customer auth vs 平台 token；建议 JWT Messenger Security 防冒用（`00q §8.2`） |

> **Workato 那条是最硬的证据**：它不是设计理念，是一个**实际存在的产品限制**——用户身份执行与后台自治执行在工程上就跑不到一起。
> **冻结**：`EmployeeIdentity ≠ EndUserCredential ≠ ServiceAccount`，且 `execution_identity_policy` 必须是显式字段（END_USER / AGENT / SERVICE_ACCOUNT / APPROVAL_REQUIRED）。

### 收敛 ④：Provider 报的状态不可信，必须自己再验一次 —— **4 家独立到达**

| 供应商 | 具体的"不可信"在哪 |
|---|---|
| Composio | **#4120：垃圾 API Key 也能创建 status=ACTIVE 的连接，26/26 复现**（`00q §10.2`） |
| Zapier | `action id` 是 ephemeral，官方要求**每次调用前重新 Get Actions**（`00q §1.2`） |
| Activepieces | Connection 错误若发生在 FlowRun 创建之前，**没有 run 可供告警捕获，调用方还可能收到 HTTP 200**（`00q §4.2`） |
| Fin | Proactive trigger **"触发成功 ≠ 目标 Procedure 一定执行"**（`00q §8.2`） |

> **冻结**：Matbox 必须把 Provider 状态与自己的状态分开建模——
> - `ACTIVE`（Provider 说的）与 `VERIFIED`（Matbox 自己探过的）是两个字段
> - `TriggerAccepted` / `ProcedureStarted` / `Completed` 三态分离
> - **Catalog 存在 / Search 可发现 / Schema 可加载 / Execute 可用 = 四个独立 Health 维度**（Composio #3776 直接证明这四者会不一致）

### 收敛 ⑤：Webhook 不是可靠消息队列 —— **3 家独立到达**

| 供应商 | 边界 |
|---|---|
| Fin | **5 秒 ACK**；4xx(非429)/5xx 通常 1 分钟后**仅再重试一次**；429 节流 1 分钟–2 小时；**超 2 小时的通知可能被丢弃**（`00q §8.2`） |
| Activepieces | Trigger hook 在正式 run 创建前失败 → 无 run、无告警、还回 200（`00q §4.2`） |
| Zapier | 正因如此才另做了 **Trigger Inbox**：lease / ack / release + ensure 幂等 + SSE（`00q §1.2`） |

> **冻结**：所有 Provider 事件先入 Matbox 自己的 Event Store，做 dedup + cursor/reconcile + 周期性 REST 对账；ACK 快路径，重活异步。**TriggerAttempt 必须独立记录，不依赖 Run 存在。**

### 收敛 ⑥：Evidence 必须 Matbox 自己长期存 —— **5 家全部保留期很短**

| 供应商 | Provider 保留期 |
|---|---|
| Zapier | Action Run **7 天** ✅ |
| Activepieces | 执行数据 **30 天** ✅ |
| Workato | Job/trigger/report **30–90 天** 📄（Activity audit 1 年） |
| Microsoft | Evaluation 结果约 **89 天** 📄 |
| Fin | 删除请求 ≤30 天；终止后 180 天自动删除 📄 |

> **没有任何一家能承担 Matbox 的业务证据责任。** 冻结：Provider 日志只能作为 Evidence **来源**，Matbox 的 Run/Evidence 是唯一 SoT。

### 收敛 ⑦：连接器数量 ≠ 能力 —— **9 家全部说了这句话**

九家的报告，无一例外都在开篇或结论处主动否定自己的连接器数字：
- Zapier「Connector 数量不重要，Action 深度、Schema、Auth、版本和 Health 才重要」
- Salesforce「一个 Connector 不是一个能力…真正给 AI 员工的是动作，不是整个 Connector」
- Composio「绝不能把 1500+ Toolkits 等同于 1500+ 可靠能力」
- Workato「不要被 12,000+ apps 营销口径带偏」
- ServiceNow「220+ 不能理解成免费拿走直接装进 Matbox」
- Microsoft「有 1,400 Connector 但 Action 深度不足」（MS-F04）
- UiPath「Preview Connector 不建议用于关键生产」
- Activepieces「Integration 覆盖不如巨头」
- Fin「Connector 在测试里通过，进入 live Procedure 仍可能失败」

> **九家同声**，这已经不是观点而是行业共识。**Matbox 的连接器验收单位必须是 `Connector + Action + 输入输出 + Scope + Risk + 真实成功 Test`，不是 App 级"已接入"。**

### 收敛 ⑧：AI 变更必须走 Eval → Release → Monitor —— **3 家独立到达**

| 供应商 | 实现 |
|---|---|
| Fin | 最完整：Preview → Batch Test(50) → Simulation → Eval → Release(full/gradual/A-B) → Monitor（`00q §8.2`） |
| Microsoft | Evaluation test set（单响应 100 / 多轮 20）+ **tool-use grader** + Release + Application Insights（`00q §2.2`） |
| Workato | Environments / RLCM / package / 双边 deployment privilege（`00q §9.2`） |

> **冻结**：任何影响 AI 员工行为的 Knowledge / Prompt / Guidance / Procedure / Policy 变更，都必须有版本、Eval、发布策略、线上 Monitor。**"改完提示词自己点两下看看"不能进生产。**

## 3｜真正的分岔：他们互相矛盾的地方

收敛之外，这几处九家给出的答案不一致，Matbox 必须自己选。

### 分岔 A：自托管到底可不可能

| 供应商 | 真实情况 |
|---|---|
| **Activepieces** | 核心 MIT 可自托管，**但开源版不含 Agents / Chat / Projects / API access / 治理层**（`00q §4.1` 官方 FAQ 逐字） |
| **Composio** | Enterprise 明确支持 run on your own cloud，**官方已有 Helm 实战排错页**（`00q §10.2`） |
| **Workato** | **OPA 不是自托管**——Runtime 仍在 Workato 云，OPA 只是私网访问代理；VPW 是专属托管（`00q §9.2`） |
| 其余六家 | 核心 Runtime 全部闭源，无自托管路线 |

> **判断**：真正能自托管且带 Agent 能力的只有 **Composio Enterprise**（需商务）。Activepieces 的自托管拿不到 Matbox 想要的那一半。**"开源"这个词在这九家里有三种完全不同的含义，收口时必须逐家看许可证边界而不是看有没有 GitHub。**

### 分岔 B：计费单位完全不统一

| 单位 | 谁 |
|---|---|
| Task（一次成功的动作步骤） | Zapier |
| Credits | Microsoft（Copilot Credits）、Activepieces、Workato |
| **Outcome（业务结果）** | **Fin**（$0.99 / $9.99） |
| Tool call + Trigger event | Composio |
| Robot + Platform Units | UiPath |
| Seat + 用量混合 | Fin（Intercom 席位 + Fin Outcome）、Microsoft（Agent 365 $15/user + Credits） |

> **Fin 的 Outcome 计费是九家里唯一按业务结果收费的**，也是唯一被自己报告点出**激励偏差**的：若"客户没再回复"就算 Resolution，系统会优化成尽快结束会话（Trustpilot 已有用户质疑）。
> **对 COST-F005 的直接输入**：Microsoft 的**双计费线**（治理按人头 $15/user/月 + 执行按 Credits）是最接近 Matbox 混合订阅+超额模型的同类对标（`00q §2.1`）。
> **冻结**：Matbox 的 `Accepted Outcome` 定义必须与任何 Provider 的计费 Outcome **分开**——退款要有 refund transaction ID，线索资格要有 CRM 接收成功。

### 分岔 C：Agent 与 Workflow 谁调用谁

- **Workato**：Recipe 可 `Assign task to genie` 并 pause 等 Agent 返回 → **Workflow 调 Agent**
- **Microsoft / Salesforce**：Agent Flow / Flow 作为 Agent 的 Tool → **Agent 调 Workflow**
- **Fin**：Procedure 既能被 Agent 意图路由触发，也能被 API 确定性触发 → **双向**
- **Activepieces**：Agent 可作为 Flow step → **Workflow 调 Agent**

> **判断**：Fin 的双向是最完整的。Matbox 应支持双向，且**关键业务流程用确定性 run endpoint 触发，不靠模型先"猜要不要走这个流程"**。

## 4｜中国：九家全部不解决，且是两种不同的缺口

这是收口里对 Matbox 最有决定性的一节。

### 4.1 缺口类型一：目录里根本没有中国平台（能力缺失）

| 供应商 | 核查方式 | 结果 |
|---|---|---|
| **ServiceNow** | Australia 版兼容性页**全量 302 行**逐条 ✅ | 零个中国平台 |
| **UiPath** | **158 个 Connector 家族**逐条 ✅ | 零个中国平台（连 Lark 都没有） |
| **Composio** | live toolkit 目录（1,467 个）定向检索 ✅ | 零个中国平台 |
| Zapier | 有 **Lark**、TikTok Lead/Conversions；未检出微信/企微/小红书/抖音/钉钉 📄 | 仅个别 |
| Microsoft / Salesforce / Activepieces / Fin / Workato | 各自报告均未列中国渠道连接器 📄 | 无 |

> 三家做了**完整目录逐条核查**（不是"搜了没搜到"），结论一致。

### 4.2 缺口类型二：有能力，但被监管切断（Workato 独有）

Workato 官方 MCP 文档逐字 ✅：
> `MCP isn't available to workspaces in the CN data center. This reflects local regulatory requirements and Workato's commitment to data sovereignty.`

可用区确认为 US / EU / AU / JP / SG / IL / KR / UK，**不含 CN**。`AI by Workato` 同样不可用。中国区使用 OAuth 的 connector 还需配置 Custom OAuth profile，且部分 connector 不可用。

### 4.3 其余几家的中国边界（各不相同，不能混为一谈）

| 供应商 | 中国状态 |
|---|---|
| **Microsoft** | M365 Copilot 不在 21Vianet；全部 AI Copilot API 在中国云不可用；**21Vianet 版 M365 本身 2026-06-01 停止新购、2027-01 停止续订** ✅ ——不是"暂不支持"，是在收摊 |
| **Salesforce** | **唯一在中国大陆正式落地的一家**：Sales/Service/Platform 自 2023-12-18 跑在阿里云上，支持 MLPS 2.0，但**大中华区由阿里云独家运营，中国区 AI 能力由阿里云大模型驱动，不是 Salesforce 自己的模型** 📄 |
| ServiceNow | 自身数据治理不满足中国本地化，需第三方（InCountry/STACKIT）或自建脱敏路线 📄 |
| Activepieces | 官方仅公开 EU / US 数据区域，**不得假定中国区** ✅ |
| Fin | AWS us-east-1 / eu-west-1 / ap-southeast-2，无中国；区域间不能迁移 📄 |

> **收口结论（本节唯一的结论）**：**中国渠道 100% 必须 Matbox 自建或走国内 Provider，九家里没有任何一家能承担。** 且这一层不能被任何全球连接器数字稀释——它对 Matbox 的实际可用性是零。
> 同时注意 Salesforce 的特殊性：它在中国"可用"，但那实际上是阿里云在运营、用阿里云的模型——**这不构成 Matbox 可依赖的 AI 员工能力**。

## 5｜Own / Reuse / Integrate / Must Not Rebuild 冻结

九家的报告各自都给了这张表，**高度一致**。以下是合并去重后的冻结版。

### OWN（Matbox 必须自己掌握，九家一致认为不能外包）

AI Employee Registry / Identity（含 Sponsor、execution_identity_policy）· Runtime Profile · Business Context · Action Registry（canonical schema / risk / version）· Connector Registry · Connection SoT（tenant-bound + vault ref）· Task / Run / Waitpoint · Tenant / Permission · Policy / Approval · **Accepted Outcome** · Evidence / Audit · Cost Ledger · Capability & Version Registry · Release / Eval / Monitor · Memory

### REUSE / PROVIDER（按场景选用，全部必须可替换）

| 场景 | 首选 Provider | 备选 |
|---|---|---|
| 全球长尾 SaaS 工具 | **Zapier**（Action Runs / MCP / SDK） | Composio |
| Agent 工具发现与长尾 Auth | **Composio**（Session + Tool Search） | Zapier MCP |
| 大企业已有系统（SAP/NetSuite/ServiceNow/私网） | **Workato**（含 OPA/PrivateLink） | Microsoft |
| 客户已在 M365/Dynamics 生态 | **Microsoft** Power Platform Connector | — |
| 客户侧对话 AI 员工 | **Fin**（POC 后决定是否真用） | 自建 |
| 无 API 的老系统 / UI 兜底 | **UiPath**（last resort） | Computer Use |
| 自控执行底座 | **Activepieces**（设计吸收为主） | 自建 |

### LEARN（吸收设计，不接产品）

Zapier 的 Partner Program + Certification + Health Score + Version Lifecycle · Microsoft 的 Harness 分层 + DLP/ACP + Solutions/ALM + Agent Identity · ServiceNow 的四层结构 + Control Tower + G0–G6 发布 Gate · Salesforce 的 Subagent/Action/Reference Action 五级拆解 + Hybrid Reasoning · Activepieces 的 Piece Contract + Waitpoint + Durable + 三次事故复盘 · Composio 的 Session + Tool Search + 四态 Health · Fin 的 Procedures + Outcome + Eval/Release/Monitor · Workato 的 Environments/RLCM + Embedded + Enterprise MCP + VUA · UiPath 的 Queue/Transaction + Job 状态机

### MUST NOT REBUILD

不从零写 9,000 个全球 SaaS 连接器 · 不重建 Microsoft 365 / Entra / Power Automate / Dataverse · 不重建完整 iPaaS 与 Enterprise API Platform · 不重建 Intercom Helpdesk 全套 · 不自研客服专用大模型 · 不重做 OPA/PrivateLink 私网基础设施 · 不重写各家官方 API client

### MUST NOT DELEGATE（九家一致）

## 6｜九家全都没碰的：Matbox 的真实护城河在哪

把九家的业务域摊开看，有一块**没有任何一家覆盖**：

| 九家覆盖的 | 九家不覆盖的 |
|---|---|
| IT 服务台 / 运维 / 安全 / 漏洞 | **家居设计与渲染** |
| CRM / 销售 / 客服 / 电商（通用） | **商品 SKU × 材质 × 尺寸 × 工艺的行业数据模型** |
| HR / 财务 / 采购 / 法务 | **设计师—厂家—经销商—终端客户的四方协作** |
| 通用文档 / 知识库 RAG | **CAD / 3D 模型 / 效果图作为一等业务对象** |
| 全球 SaaS 连接 | **中国经营渠道** |

> ServiceNow 那份报告自己写得最直白：**「设计本身不是 ServiceNow 的强业务域；Matbox 必须自己产品化。」**（`00q §5.2` 引原文）
>
> **收口判断**：Matbox 的护城河不可能是"连接器多"或"模型强"——这两条九家已经把地板抬得很高。真正只有 Matbox 能做的是：**家居设计行业的业务上下文（商品/材质/项目/设计文件）+ 中国渠道 + AI 员工的行业工作流**。九家教会我们怎么把这些做成受控可执行的系统，但内容本身没有一家能给。
