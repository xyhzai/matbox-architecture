## 0｜给忙碌读者的结论摘要

1. **原设计文档的核心判断（17个错误码清单 + ErrorResponse五字段结构）经核查方向正确，不需要推翻**，但字段设计相对RFC 9457（Problem Details for HTTP APIs，2023年生效，正式**取代**RFC 7807）和Google API错误模型存在两处可低成本吸收的真实差距：(1) `message`字段同时承担"这一类错误的稳定通用描述"和"这一次具体发生的详细解释"两个职责，RFC 9457用`title`/`detail`两个字段分开表达，这个区分对Matbox有真实价值——`title`可以安全地被日志/告警系统按错误类型聚合，`detail`才是不落库、可能含敏感度更高描述的那部分；(2) `details`字段目前定义为无结构的`jsonb`，没有约定内部至少要长什么样，本报告建议参照Google API错误模型的`BadRequest.FieldViolation`模式，给"字段级校验失败"这类最常见的details内容一个最小结构约定，而不是任由各模块各自发明。
2. **本次调研的最大新发现，是原设计文档完全没有提及、但对Stage 10施工是真实阻塞的一处冲突**：Matbox后端基座 RuoYi-Vue-Pro/yudao-cloud 自带一套`CommonResult`统一响应约定，其官方文档明确写"在标准的RESTful API的定义，是推荐使用HTTP响应状态码作为状态码。一般来说，我们实践很少这么去做"，即yudao框架的默认哲学是**HTTP响应固定返回200，真正的错误码放在响应体的`code`字段里**（0-999为系统级、后续为10位业务自定义编码）。而Matbox当前的17个错误码清单给每个码都标注了具体的HTTP状态（401/403/404/409/402/429/504/503/422/500），即假定错误会通过**真实HTTP状态码**表达。这两种哲学互斥，如果Stage 10施工时没人显式决定"Matbox错误响应覆盖yudao默认行为、走真实HTTP状态"还是"套进yudao的`CommonResult`信封、始终200"，各模块极可能各自发明，最终跨模块不一致——这正是本规范存在的目的要防止的事，必须在Stage 10前置任务里明确写死一条（本报告第11/26节给出建议：覆盖yudao默认行为，理由见第9节）。
3. **Matbox技术栈上有一个此前没人核查过的现成免费复用点**：Matbox后端是Java/Spring Boot（RuoYi-Vue-Pro基座），而**Spring Framework 6 / Spring Boot 3.0起，`ProblemDetail`类和`ErrorResponse`接口是框架原生内置能力**，直接实现RFC 9457的序列化（`type`/`title`/`status`/`detail`/`instance`五字段 + `setProperty()`任意扩展字段），`@ExceptionHandler`可以直接返回`ProblemDetail`对象无需手写JSON序列化代码。这意味着"对齐RFC 9457的字段语义"在Matbox的真实技术栈上不是"多学一个标准再自己实现"，而是"少写一层手工JSON映射代码，用框架自带能力+`setProperty()`挂上`errorCode`/`retryable`/`traceId`三个Matbox自定义扩展字段即可"，是一次真实的工作量净减少，不是净增加。
4. **跨行业调研确认的收敛结论**：本报告实查了RFC 9457/7807原文、Google API设计指南（`google.rpc.Status`+AIP-193）、以及Stripe/GitHub/Twilio三家真实SaaS的公开错误文档。收敛的共同模式是——(a) 都用一个**短字符串**（不是纯数字）作为机器可读错误标识（Stripe的`code`、GitHub的`errors[].code`、Google的`ErrorInfo.reason`，都是这种风格，**不是**RFC 9457教科书式要求的可解引用URI）；(b) 都有面向人类的`message`；(c) 都通过某种`request_id`/`trace_id`做排障关联（GitHub用`X-GitHub-Request-Id`响应头、Stripe用`request_log_url`+`Stripe-Request-Id`头、Google `RequestInfo`细节）；(d) **没有一家把`retryable`做成响应体里的显式布尔字段**——重试建议普遍通过HTTP状态码语义（429/503）+`Retry-After`头隐式表达，而不是body里一个`retryable: true/false`。Matbox当前设计里的`retryable`布尔字段，是这几家标准/大厂都没有采用、但本报告认为**仍然值得保留**的一处Matbox自己的加法（详见第9/11节：这是一个真实的、这几个参照对象都没显式覆盖的可用性缺口，AI员工需要判断某次工具调用失败能不能自动重试，比人类开发者读HTTP状态码判断更需要一个直白的字段）。
5. **最终判断：REFERENCE**——不是PASS（原设计有真实、可低成本吸收的差距，不该原样不动），不是USE（不建议把`errorCode`改成RFC 9457要求的可解引用URI风格`type`字段，这与Matbox已有17个短枚举码、以及各模块文档里"复用XX码"的既有引用方式冲突太大，收益不足以覆盖改造成本）。具体建议的字段变更见第11节，供回填 `Matbox_错误码规范_正式开发文档_V1.0-RC.md`。

## 1｜专项目标与功能边界

**这不是一个FeatureID模块，是跨模块共享契约**——不拥有独立的数据库表、独立的服务进程、独立的部署单元，管辖范围是"所有模块API出错时统一返回什么样的响应结构+错误码枚举"这一件事。

- **管什么**：定义`ErrorResponse`的字段结构（errorCode/httpStatus/message/retryable/traceId/details）；定义一份跨模块共享的错误码枚举（当前17个）及其HTTP状态映射与retryable语义；定义"新增错误码前必须先检查是否已有语义相近的码"这条治理规则。
- **不管什么**：不拥有任何一个具体错误在哪个模块的哪个业务分支被抛出（这是各模块自己的业务逻辑）；不拥有重试/超时/降级的具体策略参数（各模块第19节自行定义，只统一"用哪些码表达"）；不拥有EvidenceBundle/AgentTraceEvent的存储实现（`traceId`只是关联F-OBS-001的一个字段引用，不重复定义）。
- 这个模块唯一的"实现产出物"是：一个共享的Schema定义 + 一份错误码枚举表 + （本报告新增建议）一层Spring `ProblemDetail`序列化适配代码，供所有模块的异常处理器统一引用。没有独立Feature Register条目，因为它本身就是所有模块"错误码规范见第19节"这句话所指向的那份文档。

## 2｜Matbox架构归属

属于 **Platform Core 共享契约层**，与F-TENANT-001、F-OBS-001、F-CRED-001同属横切基础设施，但比这几个模块更底层——它没有自己的服务边界，只有一份被所有模块的`shared/errors/`目录引用的公共定义。

**依赖方向（入）**——本规范依赖：
- F-OBS-001（`traceId`关联其AgentTraceEvent，本规范不重复定义trace机制本身）
- Matbox后端技术栈基座（Java/Spring Boot，RuoYi-Vue-Pro/yudao-cloud）——本次审计新发现，第0/9节展开的`CommonResult`默认行为冲突必须在此层解决

**被依赖方向（出）**——依赖本规范的：
- 目前已确认的模块：F-ACTION-001（专项16）、F-PROVIDER-001（专项09）、F-TASK-001/AI任务运行时（专项13）、F-CRED-001（专项10）均已在各自报告第19节声明"完全复用17个跨模块错误码，不新造平行错误码体系"，经本次审计逐一复核（见第3.3节），三份报告与本规范当前文字定义**完全一致，没有发现语义漂移**。
- 未来所有模块的API端点，第19节均应引用本规范而非重新定义。

## 3｜全球方案调研结果

### 3.1 问题的真实形态

"自研 vs 复用"在契约类模块这里不是"要不要采购一个产品"，而是**"这套响应格式的字段命名/结构，要不要对齐一个已经被验证过的行业标准，而不是闭门造车"**。本次调研核查了三层参照系：

1. **正式RFC标准**：RFC 9457（现行版本，2023年发布）与它取代的RFC 7807
2. **大厂API错误模型**：Google API Design Guide的`google.rpc.Status`（被gRPC、几乎所有Google Cloud API采用，AIP-193为其权威规范）
3. **真实主流SaaS的公开错误响应实践**：Stripe、GitHub、Twilio

### 3.2 RFC 9457（Problem Details for HTTP APIs）

查证RFC原文（[rfc-editor.org/rfc/rfc9457](https://www.rfc-editor.org/rfc/rfc9457.html)）确认：

- 标准字段五个：`type`（URI，标识错误类别，默认`about:blank`）、`title`（人类可读的**稳定**摘要，"SHOULD NOT change from occurrence to occurrence"，即同一类错误的title应该固定不变）、`status`（HTTP状态码，仅作提示，生成方必须与实际响应状态一致）、`detail`（**本次发生**的具体解释，"focus on helping the client correct the problem"）、`instance`（唯一标识这一次具体错误发生的URI）。
- 机器可读的错误分类主要依赖`type`这个URI，而不是一个独立的短字符串错误码字段；规范明确"Consumers SHOULD NOT parse the 'detail' member for information; extensions are more suitable"——即不要把结构化信息塞进给人看的`detail`里，应该用扩展字段。
- **RFC 9457本身没有定义`retryable`或`trace id`这类字段**，但允许`type`定义方在扩展字段里自行加（很多真实实现确实这么做）。
- RFC 9457于2023年"obsoletes RFC 7807"（明确取代关系），新增了常见问题类型的注册表、澄清了多重问题的处理方式。**行业里旧文章/旧代码库大量还在引用RFC 7807，两者字段结构基本一致，本报告统一以现行的RFC 9457为准**。
- 内容类型为`application/problem+json`，是IANA注册的正式媒体类型。

来源：[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)、[RFC 7807](https://www.rfc-editor.org/rfc/rfc7807.html)（历史版本，仍广泛被引用）

### 3.3 Google API错误模型（`google.rpc.Status`）

查证`google.rpc.Status`定义（[status.proto](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto)）与权威规范AIP-193（[google.aip.dev/193](https://google.aip.dev/193)）确认：

- 三个核心字段：`code`（`google.rpc.Code`枚举的数字值，与gRPC状态码同源）、`message`（面向开发者的英文调试信息，明确规定"任何面向用户的信息应本地化后放入details，不要放在message里"）、`details`（`google.protobuf.Any`消息数组，携带结构化错误详情）。
- **details里最常用的标准子消息之一是`ErrorInfo`**：`reason`（UPPER_SNAKE_CASE短标识符，最长63字符，如`AUTH_UNAUTHENTICATED`这种风格）、`domain`（错误来源服务的全局唯一标识，如`pubsub.googleapis.com`）、`metadata`（补充键值对）。这个`reason`字段的命名风格与Matbox当前17个错误码的命名风格（如`TENANT_BOUNDARY_VIOLATION`）**高度一致**，是本报告认为Matbox当前`errorCode`设计方向本来就正确的一处独立验证。
- 其他标准details子消息：`BadRequest`（含`FieldViolation`数组，逐字段报告校验失败，`field`+`description`两个子字段）、`PreconditionFailure`、`LocalizedMessage`、`Help`。**没有查到`RetryInfo`被列为AIP-193的标准details类型**（gRPC生态中`RetryInfo`存在于`google/rpc/error_details.proto`，用于告知客户端"多久之后可以重试"，但AIP-193正文没有把它列为最常用标准类型，本报告不夸大其权威性，仅记录为存在但非重点）。
- HTTP映射：REST/JSON场景下`code`字段承载真实HTTP状态码（如404），另有独立的`status`字段承载`google.rpc.Code`的字符串枚举名。

来源：[google.rpc.Status proto](https://github.com/googleapis/googleapis/blob/master/google/rpc/status.proto)、[AIP-193: Errors](https://google.aip.dev/193)、[Google API Design Guide - Errors](https://cloud.google.com/apis/design/errors)

### 3.4 真实主流SaaS API错误响应实践（Stripe / GitHub / Twilio）

逐一查证公开文档（不凭训练印象）：

- **Stripe**（[docs.stripe.com/api/errors](https://docs.stripe.com/api/errors)）：错误对象字段包括`type`（枚举：`api_error`/`card_error`/`idempotency_error`/`invalid_request_error`，四个粗粒度类别，不是细粒度错误码）、`code`（细粒度、可编程判断的**字符串**错误码，如`card_declined`）、`message`（人类可读，卡错误场景可直接展示给终端用户）、`param`（指出问题出在请求的哪个参数上，便于前端定位到具体表单字段）、`doc_url`（指向该错误码文档的链接）、`request_log_url`（指向Stripe Dashboard里这次请求日志的链接，是"trace id"的一种UI化实现）。HTTP状态码是真实语义化的（400/401/402/403/404/409/424/429/5xx），**429响应文档原文写"We recommend an exponential backoff of your requests"**——重试建议是通过状态码+文字建议表达，响应体里没有单独的`retryable`布尔字段。
- **GitHub REST API**（[troubleshooting-the-rest-api](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api)）：`message`（人类可读）+`documentation_url`（指向相关文档）+可选的`errors`数组（`resource`/`field`/`code`三个子字段，逐字段报告校验问题，与Google的`BadRequest.FieldViolation`是同一种设计模式）。**trace id通过响应头`X-GitHub-Request-Id`传递，不在响应体里**（格式如`E3A2:160030:DC7C75:F76DCA:6990609D`），官方明确该值用于"correlating client-side observations with server-side logs when reporting issues"。
- **Twilio**：错误响应包含`code`（数字型Twilio专属错误码，如21611）、`message`、`more_info`（指向错误字典页面的URL，与Stripe的`doc_url`同一设计模式）、`status`（HTTP状态码）。**未查到Twilio响应体里有独立trace id或retryable字段**（本报告如实标注为"未能在公开文档中验证到"，不编造）。

来源：[Stripe Errors](https://docs.stripe.com/api/errors)、[Stripe Error Handling](https://docs.stripe.com/error-handling)、[GitHub REST API Troubleshooting](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api)、[X-GitHub-Request-Id说明](https://http.dev/x-github-request-id)、[Twilio API Responses](https://www.twilio.com/docs/usage/twilios-response)、[Twilio Error and Warning Dictionary](https://www.twilio.com/docs/api/errors)

### 3.5 收敛结论（对照Matbox当前设计逐项核对）

| 维度 | RFC 9457 | Google `rpc.Status` | Stripe/GitHub/Twilio | Matbox当前`ErrorResponse` | 本报告判断 |
|---|---|---|---|---|---|
| 机器可读错误标识 | `type`（URI风格，规范原文要求） | `code`（数字enum）+`ErrorInfo.reason`（短字符串，UPPER_SNAKE_CASE） | 短字符串（Stripe`code`/GitHub`errors[].code`/Twilio数字code） | `errorCode`（短字符串，UPPER_SNAKE_CASE） | Matbox风格与Google `ErrorInfo.reason`、Stripe/GitHub字符串码同构，**不需要改成RFC 9457教科书式的URI**，这条业界实践本身也没有严格遵守RFC字面要求 |
| HTTP状态 | `status`字段，须与实际响应一致 | `code`承载真实HTTP状态（REST场景） | 均为真实语义化HTTP状态码 | `httpStatus`字段 | 完全对齐，只是字段名不同，语义相同 |
| 面向人类的说明 | `title`（稳定）+`detail`（本次具体） | `message`（面向开发者，明确要求不要放用户可见文案） | `message` | 仅一个`message`字段，兼职两种职责 | **真实差距**：建议拆分（第11节） |
| 排障关联ID | 无标准字段，走扩展 | `RequestInfo`细节（非核心三字段） | Stripe`request_log_url`+头；GitHub响应头`X-GitHub-Request-Id`；Twilio未查到 | `traceId`（响应体字段） | Matbox把它做成响应体一等字段，比多数参照对象更完整，**保留，是加分项** |
| 是否显式`retryable`布尔字段 | 无 | 无（`RetryInfo`存在但非AIP-193重点标准类型） | 均无，靠状态码+`Retry-After`隐式表达 | 有 | **Matbox独有的加法**，业界没有先例但有真实价值（AI员工需要机器可判断的重试信号，比人类开发者读状态码语义门槛更高），建议保留，见第9节 |
| 结构化补充信息 | 扩展字段（无强制结构） | `details`数组，`BadRequest.FieldViolation`等有型模式 | Stripe`param`（单字段级）；GitHub`errors[]`（`resource`/`field`/`code`数组，同构于Google模式） | `details`（无结构jsonb） | **真实差距**：建议至少给"字段校验失败"这类高频场景约定最小结构（第11节） |

**总体判断**：Matbox当前17码+ErrorResponse设计，相对这些标准是"大方向正确、命名习惯与Google/Stripe/GitHub的字符串短码风格同构"，不是闭门造车，但存在两处真实、低成本可修的差距（title/detail拆分、details结构化），以及一处此前完全没被发现的技术栈层面冲突（yudao CommonResult默认行为）需要在Stage 10前显式决策。

## 4｜GitHub候选项目清单

## 6｜真实用户与开发者评价

本节把"真实用户评价"重新定位为**"这些标准在真实行业里的采用证据"**（契约类模块没有终端用户会写"体验差评"，能核查的是"谁在用、用得怎么样"）：

- **RFC 7807/9457的真实采用证据**：Zalando（欧洲大型电商，RESTful API Guidelines）在其官方guidelines issue中明确引用RFC 7807作为统一错误对象的依据（["Refer to RFC 7807 for the common error object"](https://github.com/zalando/restful-api-guidelines/issues/2)），落地时间可追溯到2016年，是持续多年的真实生产实践，非一次性尝试。微软的部分现代API文档（如Dynamics 365 Contact Center消息API）也遵循RFC 7807结构。
- **Spring生态的真实采用信号（对Matbox意义最直接）**：Spring Framework 6.0（2022年11月随Spring Boot 3.0发布）把`ProblemDetail`列为一等公民，多篇独立技术文章（[Baeldung](https://www.baeldung.com/spring-boot-return-errors-problemdetail)、[GeeksforGeeks](https://www.geeksforgeeks.org/advance-java/returning-errors-using-problemdetail-in-spring-boot/)、[SivaLabs](https://www.sivalabs.in/blog/spring-boot-3-error-reporting-using-problem-details/)）独立确认这不是实验性功能，`ResponseEntityExceptionHandler`已经用它处理框架内置异常（如`MethodArgumentNotValidException`），业务代码的`@ExceptionHandler`可以直接返回`ProblemDetail`对象，框架负责序列化，这是**非厂商自证的、可在Matbox自己的Spring Boot项目里直接验证的能力**，不是道听途说。
- **Google `rpc.Status`模型的真实采用证据**：这是gRPC的官方错误传输格式（几乎所有gRPC服务隐式采用），并且是Google Cloud几乎所有REST/JSON API的错误响应格式（本报告查证的多个Google Cloud产品文档页面，如People API/Chat API/Route Optimization API的错误参考页均引用同一个`google.rpc.Status`结构），是被验证过体量最大的错误模型之一。
- **Matbox自身技术栈的真实反例（本次审计新发现）**：RuoYi-Vue-Pro/yudao-cloud官方开发指南（[cloud.iocoder.cn/exception](https://cloud.iocoder.cn/exception/)）明确记录了一个与上述标准**方向相反**的真实设计决定——"在标准的RESTful API的定义，是推荐使用HTTP响应状态码作为状态码。一般来说，我们实践很少这么去做"，即该框架的默认约定是"HTTP永远200，错误码在body的`code`字段"。这是Matbox已选定后端基座**自带**的、与本规范当前设计（真实HTTP状态码驱动）直接冲突的既有约定，第9/26节展开处理方案。

## 11｜自研、复用和对齐标准的边界

- **OWN（Matbox自己拥有）**：17个错误码枚举值本身（业务语义由Matbox定义）；错误码到具体业务场景的映射（各模块自己决定何时抛哪个码，原设计不可变原则第1条已定义，本报告不改变）；`retryable`字段的语义与判断逻辑（业界无先例，Matbox自建）。
- **REFERENCE（对齐标准的字段结构，不是复用代码，也不是照搬全部字段）**：
  1. 参照RFC 9457的title/detail区分，**建议**在`ErrorResponse`中把当前单一的`message`拆分为两个字段：`title`（该错误码的稳定通用描述，可安全用于日志聚合/告警分组，值基本等同于错误码本身的人类可读版本，如`errorCode=PROVIDER_TIMEOUT`对应`title="供应商调用超时"`，同一errorCode的title理论上不随每次发生而变化）+`detail`（本次发生的具体上下文，如"哪个provider/哪次调用"，允许包含更多上下文但仍需遵守"不泄露内部实现细节"这条P0规则）。**不建议**同时引入RFC 9457的`type`（URI）和`instance`字段——`errorCode`已经承担`type`的机器可读分类职责，`traceId`已经承担`instance`"唯一标识这次发生"的职责，重复定义没有必要。
  2. 参照Google`BadRequest.FieldViolation`模式（`field`+`description`两个子字段的数组），**建议**为`details`字段里"字段级校验失败"这一类最高频场景约定最小结构：`details.fieldViolations: [{field: string, description: string}]`。其余不属于字段校验的details内容（如供应商原始错误码、审批链条上下文等）继续允许各模块自由定义，不强制统一结构，只统一"字段校验失败"这一种最常见场景，避免过度设计。
  3. Java/Spring Boot侧的**REUSE**：`ErrorResponse`的实际HTTP序列化建议基于Spring原生`ProblemDetail`扩展（用`setProperty("errorCode", ...)`/`setProperty("retryable", ...)`/`setProperty("traceId", ...)`挂载Matbox专属字段），而不是手写一套独立的JSON序列化逻辑——这是本次审计发现的真实、免费的框架级复用点，Matbox此前的原设计文档完全没有提到这一层可以怎么落地。
- **MUST NOT REBUILD（禁止重写）**：HTTP协议本身的状态码语义（不自己发明状态码含义）；JSON序列化机制本身（复用Spring框架/Jackson，不手写parser）。
- **本次审计要求显式裁定的一条边界（不属于Own/Reuse分类，是治理决定）**：Matbox的`ErrorResponse`覆盖RuoYi-Vue-Pro/yudao-cloud默认的`CommonResult`"恒200"哲学，所有`/*/`API错误响应必须返回真实HTTP状态码，`ErrorResponse`本身即为响应体，不再套一层yudao的`CommonResult{code,msg,data}`信封。这条建议写入正式开发文档的"不可变原则"或"P0冻结规则"，理由：与本报告第3.4/3.5/6节查证的全部外部标准/大厂/SaaS收敛实践一致，且这本来就是当前17码表"HTTP状态"列已经隐含的假设，只是从未被显式写成一条规则，存在被Stage 10某个模块的实现者按yudao默认习惯写成"恒200"从而破坏跨模块一致性的真实风险。

```yaml
      nullable: true
      description: >
        本报告新增建议字段：本次发生的具体上下文说明，仍需遵守P0规则
        "不泄露内部实现细节/密钥/敏感payload"（RFC 9457 detail字段语义）
    message:
      type: string
      deprecated: true
      description: >
        原设计文档字段，本报告建议逐步过渡为title+detail，
        过渡期内三者可并存，message=title与detail的拼接，保持向后兼容
    retryable:
      type: boolean
      description: "该错误是否值得客户端/AI员工自动重试，业界标准无此字段，Matbox本地加法"

      type: string
      description: "关联F-OBS-001 AgentTraceEvent"
    details:
      type: object
      nullable: true
      description: "结构化补充信息，字段级校验失败场景建议遵循以下最小结构"
      properties:
        fieldViolations:
          type: array
          description: "本报告新增建议：参照Google AIP-193 BadRequest.FieldViolation模式"
```

## 15｜OpenAPI 3.0文档

**不适用（独立OpenAPI文档意义上），理由**：本规范不是一个可独立调用的服务，没有自己的`paths`。第14节的Schema应作为`components/schemas/ErrorResponse`被所有模块的OpenAPI文档`$ref`引用，各模块（专项09第15节/专项10第15节/专项13第15节/专项16第15节）均已采用"错误码统一使用Matbox_错误码规范_正式开发文档"这一引用方式，本规范只需要保证第14节Schema定义稳定、可被`$ref`，不需要单独输出一份`openapi.yaml`。

## 16｜鉴权、权限与多租户规范

**不适用，理由**：错误响应格式本身不是一个需要鉴权的资源或端点——它是所有端点（无论该端点本身需不需要鉴权）在出错时共用的响应体格式。唯一相关的边界是P0冻结规则第3条（"错误响应永不返回provider密钥、原始敏感payload或任何可能泄露内部拓扑的信息"），这条已在原设计文档存在，本报告不新增鉴权层面的要求，只在第11节把`detail`字段的敏感度边界重申了一次。

## 17｜Provider Adapter接口规范

**不适用，理由**：本规范不对接任何外部Provider（不是F-PROVIDER-001意义上的供应商适配问题）。唯一相关之处是：F-PROVIDER-001模块（专项09）本身消费本规范来"规范化"供应商原始错误（`normalize_error`函数，见专项09报告第6.1/19节，将LiteLLM/供应商专属异常映射为`PROVIDER_TIMEOUT`/`PROVIDER_UNAVAILABLE`/`PROVIDER_REJECTED`），这是下游模块的职责，不是本规范自己的职责，本规范只提供被映射的目标枚举。

## 18｜Webhook、回调及异步任务规范

**不适用，理由**：本规范是同步HTTP错误响应的格式契约，不涉及Webhook签名校验、异步任务队列或回调去重这类机制。各模块自己的Webhook/异步规范（如专项10第18节的OAuth回调、专项16的幂等重试）在内部错误处理时复用本规范的错误码，但那是各模块的第18节职责，不是本规范要重复定义的内容。

## 19｜错误码、重试、超时和降级规范（本节即为本专项主题，从简处理避免与全文重复）

本专项本身就是"错误码规范"，第4节不可变原则/第2节调研结论已经是这份规范的核心内容，不在此处重复展开17码清单（见附录原文）。本节仅补充本次审计新增的、其他模块尚未覆盖的一条通用降级规则：

- **本次审计新增建议**：当`traceId`本身无法生成（如F-OBS-001暂时不可用）时，`ErrorResponse`仍必须返回，`traceId`字段允许为一个明确标记为"UNAVAILABLE"的占位值而非静默省略该字段——省略字段会让下游客户端的解析逻辑（假设traceId必然存在）出现空指针风险，这是原设计文档"required字段"定义里没有覆盖到的边界情况，建议在第14节Schema里把`traceId`标注为`required`但允许特殊哨兵值，而不是`nullable`。

## 20｜数据库及Migration设计

**不适用，理由**：本规范不拥有任何数据库表——它是一个响应格式契约，不产生持久化状态。`traceId`指向的AgentTraceEvent存储在F-OBS-001（其表结构已在F-OBS-001自己的正式文档定义，本规范不重复建表）。

## 21｜前后端开发任务拆分

**后端（Java/Spring Boot，RuoYi-Vue-Pro基座）**：
- BE-01 `MatboxErrorCode`枚举类（17个码+httpStatus+retryable默认值），置于`shared/errors/`公共模块
- BE-02 `ErrorResponse`/`ProblemDetail`扩展基类（复用Spring原生`ProblemDetail`，第11节REFERENCE方案）
- BE-03 全局`@ExceptionHandler`基类（`ResponseEntityExceptionHandler`扩展），供各模块继承，统一序列化逻辑，覆盖yudao `CommonResult`默认行为（第9/11节裁定）
- BE-04 `details.fieldViolations`结构化校验异常映射器（Bean Validation `MethodArgumentNotValidException`→`FieldViolation[]`的标准转换，Spring原生已部分提供，需按第11节结构对齐）

**前端**：本规范不直接产生前端UI任务，各模块自己的错误提示UI（如"该操作需要审批"）由各模块前端任务负责，只需统一按`errorCode`枚举做本地化文案映射表（一次性建立，供所有模块前端复用），不在本报告拆分为独立FE任务。

## 22｜源码目录、模块和依赖关系

```
backend/
  shared/
    errors/
      MatboxErrorCode.java          # 17个错误码枚举
      MatboxProblemDetail.java      # Spring ProblemDetail扩展，挂载errorCode/retryable/traceId
```

**依赖方向铁律**：所有模块的`shared/errors/`引用（如专项10的`credential/shared/errors/`、专项09/13/16已声明的`errors/`目录）应改为**直接依赖`backend/shared/errors/`这一个公共模块**，而不是各模块各自维护一份同名但独立实现的`errors/`目录——本次审计发现四份已完成报告（专项09/10/13/16）都各自在自己的源码目录里写了一行"errors/ # 复用Matbox_错误码规范的统一ErrorResponse"，但都没有指向同一个物理共享模块，存在"文字上说复用、代码结构上各写一份"的潜在风险，建议Stage 10统一收敛到本节定义的单一`shared/errors/`模块。

## 23｜测试集、Golden Set和验收脚本

- **ERRCODE-T001**：跨模块一致性测试——遍历F-ACTION-001/F-PROVIDER-001/F-TASK-001/F-CRED-001已声明使用的错误码，验证其HTTP状态/retryable标记与本规范第14节`MatboxErrorCode`枚举定义完全一致，不允许任何模块本地覆盖同一errorCode的httpStatus。
- **ERRCODE-T002**：yudao `CommonResult`覆盖验证——对每个模块的至少一个错误端点发起真实请求，验证响应HTTP状态码是真实4xx/5xx而非yudao默认的200（第9/11节裁定的回归测试）。
- **ERRCODE-T003**：敏感信息不落出测试——构造会触发`PROVIDER_REJECTED`/`INTERNAL_ERROR`的场景，验证`detail`/`details`字段不包含密钥、堆栈、内部服务地址（P0冻结规则第1条）。
- **ERRCODE-T004**（本次审计新增）：`traceId`哨兵值测试——模拟F-OBS-001不可用场景，验证`ErrorResponse`仍返回且`traceId`字段存在（值为约定的不可用哨兵值），不因trace生成失败而丢字段或响应500穿透。
- **ERRCODE-T005**（本次审计新增）：`details.fieldViolations`结构测试——对任一模块的参数校验类错误（如CRED-F003的`requestedScope`格式错误），验证`details.fieldViolations`按第14节结构返回，而非各模块自由格式的原始校验异常堆栈。

## 24｜成本、性能、并发及安全要求

**成本**：零采购成本——RFC/Google设计指南是公开规范，Spring `ProblemDetail`是既有依赖的一部分，不新增任何订阅/授权费用。

**性能**：错误响应序列化本身开销可忽略（与正常响应同量级JSON序列化），不构成性能瓶颈，本报告不虚构具体毫秒阈值。

**并发**：不适用，本规范不持有状态，无并发控制问题。

**安全**：
- P0冻结规则（原设计文档第6节，3条）维持不变，是本规范的核心安全约束。
- 本次审计新增：`detail`字段（第11节新增字段）与`message`字段承担同样的敏感度约束——拆分title/detail不等于detail可以放宽"不泄露内部实现细节"的要求，反而因为detail定位为"更具体的上下文"，需要额外提醒实现者不要把这层拆分误解为"detail可以更随意"。

## 27｜最终验收标准

本规范（Stage 10落地后）的验收标准 = 原设计文档P0冻结规则（第6节，3条）+ 本报告第11节字段变更回填正式文档后生效 + 第23节ERRCODE-T001~T005全部通过，且：

1. 至少F-ACTION-001/F-PROVIDER-001/F-TASK-001/F-CRED-001四个已确认依赖本规范的模块，其真实错误响应（非文档示例）逐一验证HTTP状态码/errorCode/retryable三者与本规范枚举定义一致（ERRCODE-T001）；
2. 至少一条yudao默认路由被验证已被本规范覆盖，返回真实4xx而非200（ERRCODE-T002）；
3. 敏感信息不落出测试（ERRCODE-T003）在至少一个真实触发`PROVIDER_REJECTED`的场景下通过；
4. 四个已完成模块的`shared/errors/`引用已收敛到同一物理模块（第22/26节）。

未通过任一项，本规范不得进入RC5 ACCEPTED流程，与其他专项报告"PASS≠Feature ACCEPTED"原则一致。

## 28｜交给未来AI开发人员的完整执行说明

如果你是接手这个模块施工的未来AI开发者（Codex或其他），请按以下顺序阅读和执行，不需要重新做调研或重新选型：

1. **先读原设计文档**（Stage 9正式依据，仍然有效）：`docs/Matbox_错误码规范_正式开发文档_V1.0-RC.md`——定义了17个错误码枚举、ErrorResponse基础结构（errorCode/httpStatus/message/retryable/traceId/details）、P0冻结规则，是主体施工依据。
2. **再读本报告**（本文件）——本报告不推翻17个错误码的枚举值本身，只做三处修正/新增：
   - `ErrorResponse`建议拆分`message`为`title`+`detail`（第11/14节），过渡期`message`字段保留、deprecated，不强制立即删除。
   - `details`字段建议为"字段级校验失败"场景约定最小结构`details.fieldViolations: [{field, description}]`（第11/14节），其余场景不强制统一结构。
   - **最重要、优先级最高的一条**：显式裁定Matbox的`ErrorResponse`覆盖RuoYi-Vue-Pro/yudao-cloud默认的`CommonResult`"恒200+body错误码"哲学，所有错误响应走真实HTTP状态码（第0/6/9/11/26节）——这条如果不在Stage 10开工前写进正式文档的不可变原则，极可能被不同模块的实现者按各自习惯做出不同选择。
3. **Java/Spring Boot实现建议**：不要手写JSON序列化逻辑，直接扩展Spring原生`ProblemDetail`/`ErrorResponse`接口（第7/11/21节），用`setProperty()`挂载`errorCode`/`retryable`/`traceId`三个Matbox专属字段；先确认RuoYi-Vue-Pro当前真实Spring Boot版本（与专项28第26节同一条待办联动，不重复调研）。
4. **依赖检查**：施工前确认以下四份模块报告均已声明依赖本规范且状态一致——专项09（ProviderRouter）、专项10（密钥管理）、专项13（AI任务运行时）、专项16（Action网关），均已在各自第19节写"完全复用17个跨模块错误码"，本次审计逐一复核确认四份文档与本规范当前文字**没有语义漂移**，不需要因为本报告而回头修改这四份已完成报告的第19节文字本身，只需要在真正写代码时把第22节的`shared/errors/`目录收敛到位。
5. **施工顺序**：WP-ERR-01（枚举+基类）必须最先完成，且应该早于任何消费方模块（F-ACTION-001等）开始真实的异常处理代码施工；WP-ERR-04（四模块收敛）可以晚于消费方模块各自完成初版后再统一收敛，不阻塞消费方先开工。
6. **不要重新做的事**：不要重新调研RFC 7807/9457或Google错误模型是否值得参考（本报告已系统核查，结论是REFERENCE而非USE，不要因为发现Spring原生支持ProblemDetail就误以为应该"完整切换到RFC 9457的URI风格type字段"——本报告第9节已经明确解释过为什么这样做收益不足以覆盖成本）；不要重新设计17个错误码的业务语义（本规范第2/4节已冻结）；不要在没有新证据的情况下重新讨论是否应该采购某个"错误码管理产品"（这个问题本身在第5节已经解释过为什么不成立）。
7. **如果发现本报告与真实yudao-cloud基座行为存在细节出入**（比如Stage 10核实后发现yudao近期版本对HTTP状态码处理方式有变化）：按原设计不可变原则处理，不允许因为图省事就静默按yudao默认习惯实现，发现真实冲突应记录并升级给架构负责人决策，不要自行降级本规范的HTTP状态码真实性要求。
