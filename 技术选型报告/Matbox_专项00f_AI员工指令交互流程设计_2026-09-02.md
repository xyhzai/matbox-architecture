## 0｜给忙碌读者的结论摘要

1. **这是一个真实存在、此前完全没人写过的缺口，不是伪需求**。F-TASK-001的`POST /task`、F-ORCHESTRATOR-001的`POST /orchestrator/route`两个入口API都已经定义好，但两者都隐含假设"某个前端已经把人类的意图拼装成了`goal`/`rawInput`这个字符串"——这个拼装动作本身、由谁在什么界面做、长什么样，此前完全是空白。
2. **人类指挥AI员工不是一种流程，至少是三种**，因为发起者的角色、信任层级、任务形态本质不同：①**企业内部业务操作者**（TENANT-F002定义的EmployeeOwner/Operator角色，已登录、有租户上下文，指挥自己有权限的AI员工做日常业务）；②**设计师**（角色权限上仍属于Operator/EmployeeOwner，但任务形态是本报告新发现的关键区别点——设计类指令天然是多轮、多模态的：一张参考图+一段文字+几个尺寸参数，不是一句话能说清楚的）；③**独立站匿名访客**（TENANT-F006/CRED-F009已定义的AnonymousVisitor身份，零登录、零信任、公开入口）。这三类此前从未被单独设计过交互流程。
3. **业界已经收敛出一个关键教训，值得Matbox现在就采纳**：纯聊天框（chat-only）作为Agent交互界面在2026年被证明是一种**结构性失败模式**，不是细节问题——不透明（看不到中间步骤）、二元控制（只能提交或整体中止）、无状态可见性（不知道进度）。业界新收敛的模式是"目标→任务→子任务"的**看板式进度可见层**，叠加在对话之上，而不是替代对话。OpenAI自己2026年8月停用ChatGPT Agent Mode、转向"ChatGPT Work"处理长任务，是这个教训的一个真实反面案例。这与Matbox已经设计好的F-TASK-001状态机（CREATED→...→SUCCEEDED）天然吻合，是可以直接复用的证据。
4. **本报告在核查后端契约时发现两处真实的、需要补的缺口**，不是设计判断问题：①`RoutingRequest`（F-ORCHESTRATOR-001入口）的`rawInput`字段被明确定义为"自然语言原文"，**没有附件/图片/文件引用字段**，设计师上传参考图这个动作在当前契约里无处安放；②`AiTask`（F-TASK-001）的`contextSnapshotRef`是**单数引用**，字段语义未定义是否/如何承载"多张图片+结构化参数（尺寸/预算/风格标签）"这类设计师典型的富媒体指令内容。这两处需要在Stage 10前补齐字段定义，否则设计师这条流程在契约层面走不通。
5. **提案的核心设计**：三类使用方共享同一套后端管路（Orchestrator→Task→Agent Runtime→Action Gateway→Notify），但**指令捕获界面**和**进度可见形态**按角色分层设计——企业操作者用"chat+结构化字段混合输入+任务看板"，设计师用"chat+多图上传+迭代精修"，匿名访客用"零门槛聊天气泡+受限只读能力"。具体设计见第4节，哪些是有实证支持的、哪些是本报告给出但仍需Matbox用户本人拍板的产品判断，见第5节。

## 1｜问题定义与范围边界

### 1.1 问题本身

F-ORCHESTRATOR-001原文已经把这个缺口的性质说清楚："用户在任何界面说一句话，谁/什么机制决定该找哪个AI员工处理"——但"用户在任何界面说一句话"这个动作本身，此前没有任何文档定义"哪个界面""怎么说""说的内容长什么样"。F-TASK-001的`POST /task`要求调用方已经知道`employeeId`+`goal`，同样隐含"某处已经完成了从人类意图到这个结构化请求的转换"，但转换过程是空白。

### 1.2 明确排除的相邻范围（避免重复设计）

- **AI员工的视觉/社交呈现**（头像、人设话术、"像不像真人同事"）——属于并行的00e报告范围，不在本报告内。
- **管理员的治理/监督操作**（雇佣、训练反馈、质检、成本、Control Tower）——F-CONSOLE-001已经完整设计，本报告不重复。但有一条边界必须明确画出（见下方1.3）。
- **AI员工"标准工作方式"的配置**（企业给AI员工设定长期业务流程/SOP/审批链）——这是"企业业务流配置AI员工"（专项21b）的范围，是**配置一次、长期生效**的动作，不是"这次任务具体怎么做"的一次性指令。
- **审批人（Reviewer角色）对高风险动作的批准/驳回**——这是F-ACTION-001 ACTION-F003"Action预览与确认"已经设计好的流程，Reviewer不是在"指挥AI员工做什么"，是在"对AI员工已经决定要做的某个高风险动作表态"，属于执行链路内部的一个节点，不是发起指令的入口，本报告把它当作"执行可见性"链路的一部分收纳进第4节，不单独立为第4个人设。

### 1.3 一条容易混淆、必须显式区分的边界：**"配置AI员工的标准行为"vs"给AI员工下一次具体任务"**

调研Sierra Agent Studio时发现一个关键区分（详见第3.1节）：Sierra的"Agent Studio"本质是让业务人员**配置AI员工的标准工作流/品牌语气/业务规则**——这在Matbox里对应的是AIEMP-F002（EmployeeInstance的tenant profile覆盖）+CONSOLE-F002（训练中心的行为修正反馈），是"改变AI员工以后怎么做事"的**标准配置动作**，效果持久、経AIEMP-F004审计。

而本报告要设计的是完全不同的另一件事：**业务人员今天上午想让"内容运营"AI员工帮他把这批新品图配上小红书文案**——这是一次性的、有明确开始和结束的**任务指令**，对应F-TASK-001的一个`AiTask`实例。两者调用的后端完全不同（前者改EmployeeInstance配置，后者创建AiTask），交互形态也应该不同（前者是"设置页面"，后者是"下指令+看结果"）。本报告只处理后者。

## 2｜三类真实使用方及其指令需求为何不同

### 2.1 角色与身份依据

依据F-TENANT-001 TENANT-F002已确认的7个具名角色，能"指挥AI员工做具体任务"的实际是**EmployeeOwner**（管理自己名下的AI员工，可指挥自己雇的员工）和**Operator**（可启动/取消/接管允许的任务，可能被授权指挥不属于自己但被允许操作的AI员工）——两者权限范围不同（自己名下 vs 被授权范围），但作为"发起任务指令"这个动作的执行者，UX需求基本一致，本报告在企业内部场景不再进一步拆分。TenantAdmin理论上也能做这件事（权限更高），但其典型使用场景是治理而非日常下任务，不单独设计。

**匿名访客**（AnonymousVisitor，TENANT-F006/CRED-F009）是完全不同的身份类型——会话级、零登录、租户绑定、默认零权限，只能访问显式allowlist内的只读能力，这是当前唯一已经在正式文档里定义好的"非内部用户"身份。

### 2.2 为什么"设计师"值得单独作为第二类，而不是并入"企业内部操作者"

用户明确点名"设计师"，这值得认真对待而不是简单归入"业务操作者"的子集。核查后确认关键区别**不在权限层**（RBAC角色上设计师大概率就是Operator或EmployeeOwner），**而在任务形态层**：

- 一般业务操作者的典型指令是**单轮、以文字为主**能说清楚的（"帮我把这10个SKU的标题按新规则改一遍"）。
- 设计类指令天然是**多模态、多轮迭代**的——一张房间参考图+"我要北欧风但预算控制在这个范围+这个角落有承重墙不能动"，这种指令的信息密度和形式，纯文字聊天框天然表达不全，需要图片上传+结构化参数（尺寸/预算/风格标签）+多轮"这版不错但沙发换个颜色"式的精修。

这个区别直接反映在F-AIEMP-001已定义的"初始岗位族"里——"设计支持（室内设计助理/商品匹配/资料整理）"被单独列为一个岗位族（而不是和"内容运营"混在一起），侧面印证Matbox自己的岗位体系设计者也已经意识到这类岗位的输入形态不同，只是此前没有把这个认知延伸到"交互流程"层面。

### 2.3 为什么"独立站匿名访客"必须单独设计，不能套用企业内部流程

CRED-F009/TENANT-F006已经把这个persona的身份/权限层设计完整，但明确注明"不涉及独立站具体页面/路由/内容分发设计"——即"这个人是谁、能看什么"有定义，"他怎么在界面上跟AI员工说话"没有定义。这类使用方与前两类的本质区别：**零onboarding、零学习成本容忍度、可能是第一次也是唯一一次接触**——企业内部用户可以接受"先看一下产品介绍/教程"，公开访客不会。

### 2.4 一个已排除但值得记录的候选第四人设：审批人（Reviewer）

审批人不发起指令，只对AI员工已经提出的高风险动作做决定（对应F-ACTION-001 ACTION-F003）。这不是一个独立的"指令输入"人设，而是"执行可见性"链路里的一个中断点——但它的交互体验直接影响前两类人设的"任务能不能顺畅往前走"，因此在第4节的"执行可见性"部分统一处理，不单列。

## 3｜全球参考模式调研（分人设，标注来源）

### 3.1 企业内部业务操作者——参考Salesforce Agentforce、Sierra、OpenAI Agent Mode/Work的真实经验

**Salesforce Agentforce的"Agent Script"三种输入方式**（[Salesforce Developers文档](https://developer.salesforce.com/docs/ai/agentforce/guide/agent-script.html)）：Agentforce Builder同时提供三层输入方式——①**Chat界面**：用户直接用自然语言描述想让AI做什么，系统自动转换成结构化的subagents/actions/instructions；②**Canvas视图**：把脚本汇总成可展开的可视化区块，支持`/`快捷输入表达式、`@`引用资源；③**Script视图**：面向高级用户直接写/改脚本。**这三层不是互斥选择，是同一个输入内容在不同精细度下的三种呈现**——这一点对Matbox有直接参考价值：企业内部操作者的指令输入不必是单一形态，"自然语言优先，需要精细控制时可展开结构化字段"是一个已验证的分层模式。

**Sierra Agent Studio**（[sierra.ai/product/agent-studio](https://sierra.ai/product/agent-studio)）：本质是"配置AI员工标准行为"的no-code工具（对应本报告1.3节排除的范围），不是"下一次性任务"的界面——但其"用描述而非编码来定义行为"的交互理念，与Matbox CONSOLE-F002训练中心的设计方向一致，本报告不重复评估，仅作为1.3节边界判断的佐证。

**2026年Agent UX研究的关键教训——纯聊天框是结构性失败模式**（[Agent UX Patterns: Chat-First UX Fails](https://hatchworks.com/blog/ai-agents/agent-ux-patterns/)、[Agentic UX: Frontend Design Patterns for AI Agents in 2026](https://zylos.ai/research/2026-05-28-agentic-ux-frontend-design-patterns-ai-agents/)）：聊天框作为界面的三个结构性缺陷——**不透明**（工具调用和中间推理不可见）、**二元控制**（用户只能提交新prompt或整体中止，没有中间干预点）、**无状态可见性**（看不到进度）。业界新收敛的模式是显示"目标→任务→子任务"，带owner/status/SLA/结果定义，像管理工作看板一样管理AI员工的工作，而不是翻聊天记录。这与Matbox F-TASK-001已经设计好的`CREATED→VALIDATED→QUEUED→RUNNING→WAITING_APPROVAL/WAITING_DEPENDENCY→SUCCEEDED/FAILED/CANCELLED`状态机高度吻合——**Matbox后端已经具备支撑这种看板式呈现的数据结构，只是从未设计过对应的前端形态**。

**ChatGPT Agent Mode的真实教训（含反面案例）**（[OpenAI Help Center](https://help.openai.com/en/articles/11752874-chatgpt-agent)）：用户在composer里描述任务或输入`/agent`触发，Agent执行中会在需要时暂停请求澄清/确认，用户可随时中断/接管浏览器/停止；支持"自定义指令"预设审批检查点（这与Matbox F-ACTION-001的高风险动作预览确认理念一致）。**但关键的反面证据是**：OpenAI已于2026年8月停用了ChatGPT Agent Mode，转向面向长任务/多步骤成果交付的"ChatGPT Work"——这说明"纯粹在对话框里跑一个长时间自主任务"这个产品形态，即便是OpenAI自己，也在真实运营后判断需要往"更结构化的长任务管理"方向调整，这与本节第一条"聊天框是结构性失败模式"的研究结论互相印证，不是孤例。

### 3.2 设计师——参考AI室内设计工具的多模态指令捕获模式

**图片上传+意图翻译是核心模式**（[Decorilla: AI Interior Design 2026](https://www.decorilla.com/online-decorating/ai-interior-design-for-room-design)、[Genroom: AI Interior Design Guide 2026](https://genroom.io/blog/ai-interior-design-guide-2026)）：上传房间照片后，AI先分析房间形状/光照/现有元素，再结合用户的文字指令理解要做的改造；2026年的模型能较好处理低光/广角/轻微模糊的真实手机照片，降低了"必须专业摄影"这个使用门槛。

**"Parameter Setter"模式——把模糊指令自动翻译成专业Prompt**（同上）：先进工具不要求用户自己写出精确的专业设计术语，而是有一层"意图翻译"——分析用户的简短指令，自动补全光照条件/机位角度/材质细节这类专业参数，再喂给生成模型。这对Matbox的直接参考价值：**设计师的原始指令可以是不专业、不完整的自然语言+图片，"翻译成结构化设计参数"这一步应该是AI员工/Agent Runtime内部的职责（对应RUNTIME-F001 PromptAssembler），而不是要求界面强迫设计师自己先把话说"标准"**。

**"Aesthetic DNA"式的先聊天后选型模式**（同上，Palazzo案例）：先用一轮对话式交互（上传照片+简单问答）建立起用户的风格画像，再从预定义的20-50个风格中收窄选择——这是"自由文字输入"和"结构化选项"两者结合、而非二选一的具体先例，与3.1节Agentforce"chat优先、按需展开结构化"的分层理念是同一类模式的独立收敛证据。

**迭代精修是常态，不是一次成型**：设计类任务的典型模式是"生成一版→反馈哪里不满意→再生成"的多轮循环，这与F-TASK-001已有的`POST /task/{taskId}/takeover`+`PLAN_EDITED`事件类型在语义上契合（人类中途修改执行计划），但如第6节所述，当前契约把"接管"设计成一个较重的动作，是否适合设计师这种高频次的轻量级"这版换个颜色"式追加指令，是需要补的缺口。

### 3.3 独立站匿名访客——参考IKEA、Wayfair的公开AI助手模式

**IKEA "Billie"聊天气泡——零门槛入口的具体先例**（[cosupport.ai: How IKEA Uses AI Support](https://cosupport.ai/articles/ikea-ai-support-without-losing-human-touch)）：以黄色聊天气泡形式出现在网站上，主动问候访客，提供家居设计灵感建议，覆盖购买前咨询、购买中协助、购买后支持全流程——是"零登录、点开即用"这个交互模式的真实产品先例，与CRED-F009定义的AnonymousVisitor"会话级、无需登录即可对话"完全对应。

**IKEA GPT Store助手的图片识别能力**（[Digital Commerce 360: Ikea launches generative AI assistant](https://www.digitalcommerce360.com/2024/02/06/ikea-launches-generative-ai-assistant/)）：支持访客上传照片，AI识别照片中的家具/风格并给出推荐——这进一步印证"匿名访客场景也可能需要图片输入"，不能假设匿名场景一定是纯文字，但访客上传的图片属于"只读咨询"性质（不涉及写操作、不涉及租户内部数据），与设计师上传参考图（可能进入正式设计任务、产生实际工作产出）在权限性质上不同，这条区分对应第6节要补的CRED-F009 allowlist判断规则。

**Wayfair Agent Co-pilot——一个重要的反例/对照**（[About Wayfair: Agent Co-Pilot](https://www.aboutwayfair.com/careers/tech-blog/agent-co-pilot-wayfairs-gen-ai-assistant-for-digital-sales-agents)）：Wayfair这个产品实际上是"AI辅助人类客服坐席"（AI给人类坐席推荐话术/查数据），不是"AI直接面向终端消费者对话"——这提醒Matbox在设计AnonymousVisitor流程时要明确区分"AI直接服务访客"（本报告设计的模式，对应Matbox独立站场景的公开AI员工）和"AI辅助内部客服服务访客"（不同模式，未来若需要属于另一个产品形态，不在本报告范围）。

### 3.4 三类人设共通的"进度可见性与结果交付"参考模式

已在3.1节详述"目标→任务→子任务"看板模式优于纯聊天记录，此处补充结果交付层面的证据：ChatGPT Agent Mode的"面板汇报+可中断/接管/终止"模式与Matbox F-TASK-001已有的`GET /task/{taskId}`（断线重连补齐状态）+`takeover`/`cancel`API在语义上完全对应，说明Matbox后端契约已经具备支撑这套体验的能力，缺的只是前端把它渲染出来的具体设计（见第4.4节）。

## 4｜具体设计提案：指令捕获 → 路由 → 执行可见性 → 结果交付

### 4.1 企业内部业务操作者（EmployeeOwner/Operator）

**指令捕获**：主入口是**自然语言对话框**（默认场景，覆盖大多数日常指令），叠加"按`@`选择目标AI员工/按`/`插入结构化字段（如指定预算上限、指定输出格式）"的轻量结构化能力——参照3.1节Agentforce"chat优先、按需展开"模式，不强制操作者先学会怎么"正确"下指令。

**路由**：前端把对话框内容拼装为`POST /orchestrator/route`的`RoutingRequest.rawInput`，`channel`字段填`PC`或`MOBILE`（沿用RoutingRequest已定义的枚举）；若操作者用`@`显式指定了AI员工，前端应在请求体中标注该显式选择（见第6节缺口——当前`RoutingRequest`没有"用户已手动指定target，跳过Classifier自动判断"这个字段，需要补）。

**执行可见性**：路由决策返回后创建`AiTask`（F-TASK-001），前端订阅`GET /task/{taskId}`轮询或长连接获取状态变化，按3.1/3.4节证据渲染为"任务卡片+状态标签（进行中/等待审批/已完成）+可展开的步骤时间线（映射`AiTaskEvent`序列）"，而不是把中间过程原样堆进聊天记录。任务进入`WAITING_APPROVAL`状态（对应F-ACTION-001高风险动作预览）时，前端在同一任务卡片内嵌入审批交互，不跳转到独立的"审批中心"页面打断操作者的上下文——这是本报告的设计判断（第5节标注证据强度）。

**结果交付**：任务`SUCCEEDED`后，结果通过任务卡片内联展示（文本类结果）或提供下载/预览链接（文件类结果，走F-STORAGE-001的签名下载）；同时经`POST /notify/dispatch`触发一条`INAPP`站内通知（若操作者已离开页面），`deepLink`指向该任务详情，复用F-NOTIFY-001已有的deep link路由机制，不新建平行的结果推送通道。

### 4.2 设计师

**指令捕获**：默认视图与4.1相同（对话框+结构化字段），但**新增图片/文件上传能力**——设计师可在对话框内直接拖拽/粘贴参考图、房间照片、CAD图纸等，前端先调用F-STORAGE-001的`STORAGE-F004`签名上传接口把文件传到对象存储，再把返回的文件引用与文字指令一并提交。参照3.2节"Aesthetic DNA"模式，可选提供一层轻量风格标签选择（如预设风格类目）作为文字描述的补充而非替代，降低设计师把风格意图完全用文字表达清楚的负担。

**路由**：这是第6节要补的核心缺口所在——`RoutingRequest`当前的`rawInput`只能装文字，没有字段能装"这次请求附带了3张图片+2个结构化参数"这件事。提案：在`RoutingRequest`增加`attachments[]`字段（每项为一个F-STORAGE-001文件引用+类型标注，如`REFERENCE_IMAGE`/`ROOM_PHOTO`/`DIMENSION_DOC`），供Classifier判断是否需要路由到"设计支持"类AI员工（多模态附件本身就是一个强路由信号，理论上比纯文字更容易判定意图）。

**执行可见性**：设计类任务天然多轮，建议在4.1的任务卡片基础上增加"版本对比"视图——每一轮AI产出作为一个版本节点，设计师可以在时间线上回看/对比历史版本，而不是只看最新结果覆盖旧结果。**中途追加指令**（"这版沙发换个颜色"）应该走一个比`takeover`更轻量的路径——见第6节，当前契约里"接管"语义偏重（"标记后续步骤需要人工确认"），不完全等同于"我要在当前任务基础上补一句话"，这是需要补的API缺口，不是前端可以自己绕过去的问题。

**结果交付**：与4.1一致，但结果预览应支持图片/渲染图的内联大图查看（不只是文件下载链接），这是纯前端展示层的决定，不涉及后端契约变更。

### 4.3 独立站匿名访客（AnonymousVisitor）

**指令捕获**：参照3.3节IKEA Billie模式，采用**聊天气泡**形态嵌入独立站页面，访客无需登录直接输入文字（可选上传照片，用途仅限"识别/咨询"，不触发正式设计任务）。触达`POST /cred/visitor-sessions`（CRED-F009）先签发`AnonymousVisitorSession`，会话内携带该visitorSessionId调用后续接口。

**路由**：`RoutingRequest.channel`填`独立站匿名入口`（沿用已有枚举值），`actorId`使用`visitorSessionId`而非人类`userId`；根据TENANT-F006"默认零权限+allowlist"原则，访客发起的请求只能路由到该租户明确标记为"公开可用"的AI员工（这要求`EmployeeInstance`或`EmployeeTemplate`需要一个"是否允许匿名访客访问"的可见性标记——需核查AIEMP-F002当前schema是否已有此字段，若无，也是一处需要补的关联缺口，本报告在此提示，不越权替F-AIEMP-001下结论）。

**执行可见性**：访客场景不适合4.1的任务看板（访客大概率不会长时间停留等待、也没有"任务列表"心智），应保持**同步或准同步的对话式呈现**——AI员工的回复直接在聊天气泡内流式呈现，不暴露`AiTask`状态机细节。若访客的请求触发了需要人工审批或长时间执行的任务（理论上应该很少见，因为allowlist本身限制了访客能触发的动作类型都应是低风险只读类），需要有明确的降级话术（"这个请求需要人工介入，请留下联系方式"），自然衔接到CRED-F009已定义的"身份升级"流程。

**结果交付**：直接在对话气泡内交付；若访客后续留资/下单，触发`POST /cred/visitor-sessions/{visitorSessionId}/link`身份升级，此前的对话上下文按CRED-F009已有设计随会话关联转移到正式Contact身份，不丢失。

### 4.4 三类人设共通：执行可见性中的审批中断点（Reviewer介入）

不论哪类人设发起的任务，一旦触发`WAITING_APPROVAL`（F-TASK-001状态）+ F-ACTION-001的高风险动作预览，Reviewer角色需要在自己的界面（可能是独立的"待审批"列表，也可能是收到通知后跳转到具体任务详情页）做出决定。这条链路本身已经被F-ACTION-001（ACTION-F003）和F-NOTIFY-001完整定义（通知Reviewer、deep link跳转到具体资源），本报告不重新设计，只强调：**发起指令的人（4.1/4.2的操作者）应该能在自己的任务卡片里实时看到"正在等某某审批"这个状态，而不是任务卡片停在原地不给任何解释**——这是任务卡片状态渲染逻辑的一部分，不是新的后端能力需求。

**产品先例参照（2026-09-02补充，专项00i核查OpenWorker后回填）**：OpenWorker（andrewyng/openworker）的"Inbox"统一收件箱模式——把所有待批准项（不论来自哪个session、哪个工具）汇总到一个界面，未及时处理的持续挂起等人工review——是"发起指令的人应该实时看到审批状态"这条设计判断的一个真实、可运行的产品先例，与3.1节Agentforce/ChatGPT Work并列引用。**不构成新的设计判断，只是给已有判断补一条独立验证来源**（详见`Matbox_专项00i_OpenWorker专项评估_2026-09-02.md`第6节）。

## 6｜现有后端契约暴露出的真实缺口（本报告的核心发现）

以下是核查过程中确认的、独立于本报告设计判断之外的**客观契约缺口**——即便Matbox最终采用与本报告不同的具体UI设计，这些缺口依然存在，需要在Stage 10前修补：

### 6.1【确认缺口】`RoutingRequest`没有附件字段

F-ORCHESTRATOR-001正式文档第5节定义`RoutingRequest`为：
```
requestId, tenantId, actorId, rawInput（自然语言原文）, channel, context{}, createdAt
```
`rawInput`被明确标注为"自然语言原文"，是纯文本语义。设计师上传的参考图/房间照片/尺寸文档，在当前schema里**没有任何字段可以承载**，只能被迫塞进`context{}`这个未强定义结构的自由字段里（不安全，容易被不同模块各自定义不兼容的用法）。

**建议**：`RoutingRequest`显式新增`attachments[]`字段，每项为`{fileRef（F-STORAGE-001文件引用）, attachmentType（REFERENCE_IMAGE|ROOM_PHOTO|DIMENSION_DOC|OTHER）}`，供Classifier判断路由（附件类型本身是路由信号）并向下游透传。

### 6.2【确认缺口】`AiTask.contextSnapshotRef`语义未定义能否承载多文件+结构化参数

F-TASK-001正式文档第5节`AiTask`的`contextSnapshotRef`是单数引用字段，文档没有说明这个引用指向的对象内部结构是否支持"多张图片+尺寸/预算/风格标签"这种设计师典型的复合输入。如果Stage 10实现时`contextSnapshotRef`被实现成只能指向单一文本快照，设计师这条流程在数据层面就走不通。

**建议**：在F-TASK-001 Stage 10施工前，明确`contextSnapshotRef`指向的对象schema，至少要能承载"结构化字段+多个文件引用数组"，不能假设它只是一段文本。

### 6.3【确认缺口】没有"用户已手动指定AI员工，跳过Classifier"的字段

参照4.1设计（用户用`@`显式选择目标AI员工），当前`RoutingRequest`没有字段能表达"这次不需要Classifier判断，用户已经明确指定"。若不补这个字段，用户显式选择后系统仍会跑一遍Embedding/LLM路由判断，一是浪费ORCHESTRATOR-F004已经要求独立计入成本的编排开销，二是理论上存在"用户明确选了A，但Classifier判断应该是B"的冲突场景，当前文档未定义此时以谁为准。

**建议**：新增`explicitTargetEmployeeId`（可选字段），非空时Classifier直接跳过，Coordinator直接以此创建AiTask，同时仍记录一条`RoutingDecision`（`routingMethod`枚举需要新增`USER_EXPLICIT`）用于审计追溯，不破坏ORCHESTRATOR-F005"路由决策留痕可查询"的要求。

### 6.4【确认缺口】"中途轻量追加指令"没有对应的API

F-TASK-001定义了`POST /task/{taskId}/takeover`（人类接管，标记后续步骤需要人工确认）和`AiTaskEvent`里的`PLAN_EDITED`事件类型，但两者语义都偏"接管控制权"，没有定义一个更轻量的动作：**人类在任务仍由AI主导执行的情况下，中途补充一句话/一个参数**（如设计师的"这版沙发换个颜色"，或操作者的"预算上限改成8000"）。当前唯一路径是先`takeover`（获得控制权）再想办法编辑计划，这对高频次的轻量追加场景显得过重，且`takeover`后"标记后续步骤需要人工确认"这个副作用可能不是用户想要的。

**建议**：本报告不代为决定具体实现（可能是新增`POST /task/{taskId}/append-instruction`轻量端点，也可能是放宽`PLAN_EDITED`的触发门槛使其不依赖`takeoverFlag`），但需要F-TASK-001的下一次修订正式定义这个动作，否则设计师场景的"迭代精修"体验会被迫走一个过重的接管流程。

**风险提示（2026-09-02补充，专项00i核查OpenWorker后回填）**：OpenWorker解决同一问题（中途补一句话）的方式，是把对话session本身当作执行的持久化主线索——直接在同一个聊天会话里继续说话。**这条不能直接照搬**：它与架构原则第41条（参照OpenAI Work模式、明确否决纯聊天驱动）存在真实张力，Matbox的`AiTask`是无状态对话贯穿的结构化任务实例，不是可以无限追加的会话。下次修订本节方案（新API端点 vs 放宽事件触发条件）时，需显式规避"把AiTask无意中做成聊天会话"这个具体陷阱（详见`Matbox_专项00i_OpenWorker专项评估_2026-09-02.md`第5节）。

### 6.5【需F-AIEMP-001核实，本报告不越权下结论】AI员工是否有"允许匿名访客访问"的可见性标记

4.3节设计要求：能路由给匿名访客的AI员工，必须是租户显式标记为"公开可见"的那些，不能所有AI员工默认对匿名访客可见。核查`EmployeeTemplate`/`EmployeeInstance`当前schema（F-AIEMP-001第5节），未发现类似`visibilityScope`或`publicFacing`这样的字段。这有可能是本报告发现的一处关联缺口，但因为不在本报告直接负责的模块范围内，只作为发现记录在此，交由F-AIEMP-001下次修订时核实是否需要补充，不代为决定。

## 7｜遗留给用户拍板的开放问题（研究无法替代的产品判断）

1. **企业操作者v1要不要做"@指定AI员工/`/`插入结构化字段"这层复杂度**，还是先用最简单的纯chat+自动路由跑起来，等真实用户反馈"总路由错"再加——这是范围/优先级判断，第5节已标注。**命名/分级参照（2026-09-02补充）**：OpenWorker真实验证过的五档权限模式命名（discuss/plan/interactive/auto/custom，对应"只读讨论/只读规划/逐次询问/限定路径全自动/工具白名单自定义"）可作为这层控制粒度的具体命名参考，是否v1采用仍需用户拍板（详见`Matbox_专项00i_OpenWorker专项评估_2026-09-02.md`第6节）。
2. **设计师场景要不要做"设计工作台"式的独立界面**（类似专业设计软件的画布+图层+版本对比），还是复用同一套chat+上传界面加轻量版本视图——这直接决定前端技术栈选型（是否需要引入画布/图层渲染能力），成本差异大，需要用户结合真实设计师用户规模判断值不值得投入。
3. **匿名访客的会话保留策略**（未登录状态下"稍后继续对话"要不要支持、依赖什么机制保持会话）——这属于CRED-F009自己已经注明"不涉及独立站具体页面设计"的范围，本报告同样不代为决定，需要等用户提供的"独立站"业务包到达后一起设计。
4. **进度可见性UI具体做成什么形态**——3.4节证据支持"目标→任务→子任务"看板模式优于纯聊天记录，但Matbox要不要在v1就做完整看板视图，还是先在chat界面内做最小可行的内联进度条/状态标签，是需要用户结合开发资源判断的优先级问题，不是研究本身能替代的决定。
5. **6.4节"轻量追加指令"具体该怎么实现**（新API端点 vs 放宽现有事件触发条件）——本报告已标注这是确认存在的契约缺口，但具体技术方案属于F-TASK-001下次修订该做的设计工作，不属于本报告范围内可以替代下的判断。
