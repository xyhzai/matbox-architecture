## 0｜给忙碌读者的结论摘要

在深入28节之前，先直接回答用户最关心的问题：**这两个Feature是不是"体验层，没什么好选的，直接自研"这句话的自我循环论证？**

**核查结论：CONSOLE-F004/F005本身确实没有第三方产品能替代（这是核查后的结论，不是默认结论），但核查过程发现四处此前文档没有写清楚、甚至写错了的地方，本报告逐一修正：**

1. **CONSOLE-F004原设计"REUSE: F-COST-001账本与预算告警"这句话背后引用的成本追踪机制已经过时，本报告予以修正**——`Matbox_AI员工管理控制台_正式开发文档_V1.0-RC.md` 第48行把 F-COST-001 描述为"账本与预算告警"没有点名具体技术路径，而 `Matbox_成本控制_正式开发文档_V1.0-RC.md` 第51行原始的 Own/Reuse 表仍写着"REUSE: Langfuse 的调用链路成本记录能力"。但 `Matbox_专项05_成本控制_技术选型与开发交接报告_2026-08-30.md` 已经用完整的12点方法论核查后**推翻**了这条 REUSE，最终技术路线是 **COST-F001 改为 Matbox 自研聚合层（消费 F-OBS-001 的 `AgentTraceEvent` + F-PROVIDER-001 的 `ModelInvocation`，自维护官方计价表）**，Langfuse 降级为可选、非P0的开发者调试工具，理由包括 Langfuse 存在真实、当前在 GitHub Issues 追踪器中开放的成本计算错误（o3模型成本计算偏差达400%，GitHub Discussion #7902）以及 2026年1月被 ClickHouse 以约4亿美元估值收购带来的整合不确定性；COST-F005（企业套餐用量账本）则是 **Postgres 事务型账本**（行锁+唯一idempotencyKey约束+仅追加表），全程未采购 OpenMeter/Lago 等候选。**这意味着 CONSOLE-F004 作为"F-COST-001的自助体验层"，它读取/展示的底层数据源是 Matbox 自己的 Postgres 账本表（`cost_usage_ledger_entry`/`budget_reservation`/`entitlement`），不是 Langfuse trace 数据**——这条修正直接决定了 CONSOLE-F004 成本预测功能应该查询哪张表，如果继续按原设计文档字面意思去接 Langfuse，会接错数据源。
2. **成本预测子能力：原设计已经预留了"占位、Stage 10定具体模型"的正确直觉，本报告用真实候选核查确认这个直觉是对的，并给出具体方法**——用户特别要求核查 Prophet（Meta）、statsmodels、简单移动平均/线性回归三类方案是否适合 Matbox"少量租户、日/月粒度、非大数据规模"的真实数据形状。核查结论：Prophet 目前处于**维护模式**（v1.4.0，2026年8月发布，仅接受bug修复，不再新增功能），MIT协议，但它的核心价值主张（拟合强季节性）要求"several seasons of historical data"（官方文档原文），且真实 GitHub Issue（#783 "Minimum number of data points"、#1252 "Improve predict speed on small dataset"）证实它在小数据集上存在真实的预测速度/最小样本量摩擦——这些证据合起来说明 Prophet 对 Matbox 当前阶段（新产品、租户数量少、大概率没有跨年度的完整季节性历史数据）是**过度工程**。statsmodels（ARIMA/指数平滑）技术路线成熟、BSD-3协议、维护活跃，但同样要求引入一个 Python 运行时依赖（Matbox 后端是 Java + Next.js 混合栈），对"参考预测、非承诺值"这条产品定位（P0冻结规则第2条）来说投入产出比不划算。**最终结论：P0阶段用 Matbox 自研的简单趋势外推（移动平均+线性回归），零新依赖，statsmodels 作为有明确触发条件的监控候补，Prophet 不采纳。**
3. **成本预测品类里被专门核查、确认"形状不对"的候选：OpenCost / Kubecost**——用户要求核查这两个 FinOps 开源工具是否相关。核查结论：两者都是 **Kubernetes 集群成本分摊（cost allocation）** 工具，解决的是"把已经发生的云账单按 Pod/Namespace/Label 拆分"这个问题，不是"预测未来会花多少钱"；且 Kubecost 已被 IBM 收购、商业化程度更高。这个品类与 CONSOLE-F004 需要的"基于历史用量趋势外推未来花费"完全是不同问题，本报告确认排除，不是没找到就跳过。
4. **CONSOLE-F005 Control Tower：没有任何BI工具或"AI治理仪表盘"产品可以替代聚合逻辑本身，但原设计遗漏了一个真实的权限视角缺口，本报告新增修正**——原设计 `GET /console/control-tower/digest/{tenantId}` 只有"按租户查看"一种形态，但 Control Tower 的典型使用者不只是租户管理员，Matbox 平台自己的运营/风控人员（PlatformAdmin）同样需要一个跨租户的全局态势视图（比如"哪些租户的Secure支柱亮红灯""平台整体预算健康度"），这是 ServiceNow AI Control Tower 案例（罗利市政府/霍尼韦尔/Avalara）里客户价值的重要组成部分，原设计文档没有区分这两种视角，本报告在第13/16节把这个缺口补上，新增 `GET /console/control-tower/digest`（不带tenantId，仅PlatformAdmin可访问，跨租户汇总）作为CONSOLE-F005新增P0端点。至于"前端用什么渲染这五个支柱"这个真正需要选型的问题，本报告核查了 Grafana/Metabase/Apache Superset 三个真实BI平台候选（全部因License/架构定位问题不采用，详见第3.2/9.2节）以及"AI治理仪表盘"这个用户特别要求核实的细分品类（未找到可采纳的现成开源产品，详见第3.3节），最终给出 Matbox 现有 Next.js 前端栈内的图表组件库Top-3排名（ECharts为主、Recharts为辅），这是 F-CONSOLE-001 系列第一次对这个问题给出有真实证据支撑的结论。

其余部分（CONSOLE-F004的预算自助配置界面、CONSOLE-F005的五支柱信息架构本身）经核查确认原设计方向正确，只是需要补齐与已修正的F-COST-001数据源、新增权限视角对齐的具体实现细节，本报告一并补齐。

## 1｜专项目标与功能边界

**CONSOLE-F004（成本+预算中心）** 解决的问题：**租户管理员自己能看懂"AI员工这个月/这个季度花了多少钱、还能花多少、照现在这个花钱速度下去月底/季度末大概要花多少"，不用工程师帮忙查数据库或看Grafana。**

- **管什么**：把 F-COST-001（COST-F001~F005）已有的记账数据投影成租户管理员能看懂的界面；把预算规则/阈值的配置从"改数据库/工单"变成"管理员自己在界面上改"；新增此前完全不存在的**成本预测**能力——基于历史用量趋势给出"照当前趋势，本月/本季度预计花费"的参考值。
- **不管什么**：不重新记账（COST-F001~F005是唯一事实源）；不做自动阻断（预测结果只能触发提醒，P0冻结规则第2条）；不做通用FinOps平台（不解决云基础设施成本分摊，只解决AI调用/用量成本）。

**CONSOLE-F005（统一控制台/Control Tower）** 解决的问题：**管理员打开控制台首页，不用分别点开5个不同模块的页面，就能看到"我的AI员工整体运转得怎么样"这个问题的答案，按 Discover/Observe/Govern/Secure/Measure 五支柱组织。**

- **管什么**：把 CONSOLE-F001~F004 以及 F-ORCHESTRATOR-001（路由健康）、F-SUPERVISOR-001（输出治理）、F-TENANT-001（权限/身份）的关键指标聚合到一个页面；提供跨模块下钻入口；区分 TenantAdmin（本租户视角）与 PlatformAdmin（跨租户视角，本报告新增，见第0/13节）两种视图。
- **不管什么**：不做 Measure 支柱下的 ROI/Value 具体算法（调研清单#17仍为🟡，需要真实业务结果数据）；不做全公司策略决策中枢（参照 Medallia 真实差评，CONSOLE-F003已确立这条边界，CONSOLE-F005同样适用）；不拥有任何被聚合模块的事实数据，纯投影。

两者的共同点：都是"体验层"，都不新增业务事实源（CONSOLE-F004的`BudgetForecast`、CONSOLE-F005的聚合摘要，原设计文档都明确标注"投影计算结果，可缓存不必持久化"），这决定了本报告的选型问题天然被限定在两类：(1) 预测算法这一具体计算逻辑该怎么实现；(2) 聚合结果该用什么技术渲染/呈现，不是"要不要重新设计后端记账/治理能力"。

## 2｜Matbox架构归属

CONSOLE-F004/F005 与 CONSOLE-F001/F002/F003 同属 **面向租户管理员的第一方产品体验层**（F-CONSOLE-001域），不是独立技术基础设施。

**依赖方向（入）**：

- CONSOLE-F004 依赖 **F-COST-001 全部**（COST-F001~F005），具体到表层面：`cost_usage_ledger_entry`（COST-F005账本，Matbox自研Postgres事务表，见第0/9节修正）、`budget_rule`/`budget_alert_event`（COST-F002/F003）、`entitlement`（COST-F005权益表）。
- CONSOLE-F005 依赖 CONSOLE-F001~F004（含本报告的CONSOLE-F004产出）、F-ORCHESTRATOR-001（路由健康信号）、F-SUPERVISOR-001（MonitorReview/输出治理信号）、F-TENANT-001（权限/身份态势，Secure支柱数据源）、F-OBS-001（Observe支柱底层证据）。
- 两者都依赖 F-TENANT-001 做鉴权与多租户/跨租户视角区分（见第0/16节新增内容）。

**被依赖方向（出）**：CONSOLE-F005 是 F-CONSOLE-001 内部唯一"消费其余4个Feature产出"的下游，不存在其他模块反向依赖 CONSOLE-F004/F005 的情况（两者都是终端展示层，不对外提供被其他后端模块调用的API）。

**架构关键约束（本次审计确认，与CONSOLE-F001~F003一致）**：CONSOLE-F004/F005 只拥有自己的**投影计算缓存**（可选，见第20节），不拥有任何业务事实表；`BudgetForecast`/`ControlTowerDigest` 任何时候都可以从底层模块数据重新计算得到，不是不可再生的数据。

## 3｜全球方案调研结果

### 3.1 CONSOLE-F004 成本预测：品类现状

"基于历史用量预测未来花费"这个具体问题在2026年有三层现成方案，此前任何 Matbox 文档都没有系统对比过：

1. **通用时间序列预测库**（Prophet、statsmodels、darts、NeuralProphet）：Python生态，需要独立计算服务或子进程调用。
2. **朴素统计外推**（移动平均、线性回归、指数平滑的简化形态）：任何语言都可以几十行代码实现，不需要额外依赖。
3. **FinOps/云成本管理平台自带的预测功能**（OpenCost、Kubecost、CloudZero、Finout）：面向"云基础设施账单"场景，用户特别要求核查是否适用于 Matbox 的"AI调用成本"场景。

`Matbox_专项05` 已经确认 Finout 等企业级FinOps SaaS平台"团队规模不需要、且是托管服务，与自建优先原则冲突"，本报告在此基础上专门核查 OpenCost/Kubecost 这两个**开源**FinOps工具是否是漏掉的选项（见3.3节），以及三类时间序列方案里哪个最匹配 Matbox 真实数据形状。

### 3.2 CONSOLE-F004"直接引入一个现成时间序列预测库"的正面核查（方法论第2条）

逐一核查 Prophet / statsmodels / 简单趋势外推 是否应该被 Matbox 采纳为 P0 预测方法：

| 排名 | 方案 | 部署方式 | License/维护状态（2026-09核实） | 是否需要新增运行时/依赖 | 排名理由 |
|---|---|---|---|---|---|
| **#1** | **Matbox自研（移动平均+线性回归趋势外推）** | 全部自托管，纯业务代码 | 无License问题 | 否——直接用现有后端语言（Java）实现，或Next.js端用TypeScript实现均可 | 唯一零新增依赖、可解释性最强（"过去N天日均花费×本月剩余天数"这种计算，管理员一眼能懂"为什么是这个数字"）、且与产品定位"参考预测、非承诺值"（P0规则）精确匹配的方案；下方两个候选提供的额外精度在当前数据量级下无法验证是否有实际收益 |
| **#2** | **statsmodels（ARIMA/Holt-Winters指数平滑）** | 需要Python运行时（子进程或独立微服务），BSD-3 | 成熟、维护活跃，Python科学计算生态标配 | 是——Matbox后端是Java+Next.js，需要新增Python执行环境 | 技术路线成熟、适合30-300个观测点的场景（与Matbox早期租户的数据量级接近），但要为"参考预测"这个低风险功能引入一个新的运行时依赖，投入产出比在当前阶段不成立；列为**监控候补**，触发条件见第9.1节 |
| **#3** | **Prophet（Meta）** | 需要Python运行时，MIT | v1.4.0（2026-08-15发布），**维护模式**：仅接受bug修复/依赖升级，不再开发新功能 | 是——同statsmodels，且Prophet本身依赖PyStan/CmdStanPy，环境更重 | 官方文档明确其价值在于"strong seasonality"场景，需要"several seasons of historical data"，真实GitHub Issue（#783/#1252）证实小数据集下存在最小样本量和预测速度摩擦；对Matbox当前阶段（新产品、租户少、大概率不到一年的历史数据）是过度工程，排第3 |

**#1为什么胜过#2/#3**：CONSOLE-F004原设计文档自己已经把预测方法定义为 `method(TRAILING_TREND，占位)`，本次核查的价值不是推翻这个直觉，而是**验证它是对的并给出具体实现**——Prophet/statsmodels解决的是"如何精确捕捉季节性/趋势变化点"这个问题，但这个问题的前提是"有足够长、有季节性模式的历史数据"，Matbox当前阶段（新产品、Stage 10尚未开始真实部署，见第7节F-COST-001继续断点）并不具备这个前提；即使未来具备了，产品定位本身也明确要求"参考预测、非承诺值、只能触发软性提醒"（P0规则），不需要为了提升几个百分点的预测精度承担新增Python运行时的工程/运维成本。这不是"偷懒选简单方案"，是核查后确认复杂度与场景不匹配。

### 3.3 CONSOLE-F004 FinOps开源工具核查：OpenCost / Kubecost（用户特别要求核实）

- **OpenCost**：CNCF项目，核心能力是"按Kubernetes集群/Namespace/Pod/Label做实时成本分摊"，面向已经发生的云基础设施账单二次归因，不提供"预测未来花费"作为核心特性（[OpenCost官方博客](https://opencost.io/blog/)、[CloudZero对比文章](https://www.cloudzero.com/blog/open-source-cloud-cost-management/)交叉印证）。
- **Kubecost**：2024年被IBM收购后并入IBM云成本/FinOps产品线，商业化程度更高，同样是Kubernetes成本分摊/优化工具（[CloudZero: Kubecost vs OpenCost](https://www.cloudzero.com/blog/kubecost-vs-opencost/)）。
- **结论**：两者解决的都是"云基础设施账单怎么按资源维度拆开看"，Matbox的场景是"AI调用/Token/存储等用量账本怎么预测未来趋势"，问题类型完全不同——即使Matbox未来真的需要管理云基础设施成本（区别于AI调用成本），OpenCost也是届时才需要评估的独立问题，与CONSOLE-F004当前范围无关。本报告确认这是一次"专门核查后排除"，不是想当然跳过。

### 3.4 CONSOLE-F005"直接引入一个现成BI/仪表盘平台"的正面核查（方法论第2条，最重要的问题）

逐一核查 Grafana / Metabase / Apache Superset 三个真实自托管BI/可视化平台是否可以让 Control Tower 放弃"Matbox自己写聚合API+自己渲染五支柱页面"，改用其中一个：

| 排名 | 方案 | 部署方式 | License（2026-09核实） | 能否理解Matbox跨模块领域语义 | 排名理由 |
|---|---|---|---|---|---|
| **#1** | **Matbox自研聚合API + Next.js前端渲染（图表组件见3.5/9.2节）** | 全部自托管，复用已决定的Next.js栈 | 无License问题 | 是（本来就是为此设计） | 唯一理解"五支柱分别对应哪个后端模块的哪个字段、PlatformAdmin和TenantAdmin该看到什么"这套Matbox专属信息架构的方案 |

### 3.5 CONSOLE-F005"AI治理仪表盘"细分品类核查（用户特别要求，比通用BI工具更具体的品类）

用户特别要求：搜索"AI governance dashboard"这个更具体的品类，不要止步于通用BI工具对比。核查结果：

- **没有找到符合"聚合多个AI运营/治理后端信号到一个五支柱式仪表盘"这个具体定位的、可采纳的开源产品**。搜索命中的项目分三类，逐一核查后均不构成CONSOLE-F005的替代候选：
  1. **Agent运行时治理/策略执行工具包**（Microsoft Agent Governance Toolkit、`awesome-ai-agent-governance`收录的项目）——这些解决的是"运行时拦截Agent的越权动作/提示注入"，是Matbox自己F-SUPERVISOR-001/F-TENANT-001已经在做的事，不是"把已有信号聚合展示"这个CONSOLE-F005的问题（[Microsoft Open Source Blog](https://opensource.microsoft.com/blog/2026/04/02/introducing-the-agent-governance-toolkit-open-source-runtime-security-for-ai-agents/)）。
  2. **Microsoft Responsible AI Toolbox**（`github.com/microsoft/responsible-ai-toolbox`，MIT，真实、成熟的开源项目）——它的"Responsible AI Dashboard"是给数据科学家debug**单个已训练模型**的公平性/可解释性/错误分析用的（Error Analysis/Interpretability/Fairness四个组件），面向的是模型开发阶段，不是Matbox需要的"运行时跨5个后端模块的运营态势聚合"，品类名字像但问题不是同一个。
  3. **AgentOps**（`github.com/agentops-ai/agentops`，MIT，5.6k star，真实活跃）——它的"dashboard"是LLM调用会话回放/成本追踪的可观测性产品，与`专项03/05`已经系统核查过的Langfuse/Helicone同属一类（LLM可观测性平台自带面板），已经在那两份报告里因为"整体平台替代不成立""成本计算权威性不足"等理由被否决，本报告不重复核查，直接沿用结论。
- **商业化头部产品**（Credo AI、Holistic AI、ServiceNow AI Control Tower本身、IBM watsonx.governance）已经是原始Console设计文档研究过的对象（见调研清单#18），本报告不重新核查这些品牌本身，只确认一点新证据：**Credo AI 唯一的开源组件 Credo AI Lens（责任AI评估框架）已于2024年归档**（[Kosmoy对比文章](https://www.kosmoy.com/resources/blog/credo-ai-alternatives/)），进一步印证"成熟的开源AI治理仪表盘产品"这个品类目前不存在可采纳的选项。
- **结论**：与`专项01`"没有一个工具打通全部"的模式重复出现——AI治理仪表盘这个更具体的品类里，同样没有找到能替代Matbox自己聚合逻辑的现成产品，本报告确认原设计"Matbox自研聚合视图"的方向正确，且这次是覆盖了用户特别指定的细分品类之后得到的结论，不是只看了通用BI工具就下结论。

### 3.6 CONSOLE-F005 真正需要选型的问题：前端图表渲染层

排除了"整体BI平台替代"和"AI治理仪表盘产品替代"两条路之后，Control Tower剩下的真实技术决策是：**在已经确定的Next.js前端里，用什么组件库渲染五支柱页面（健康度仪表盘/状态网格/趋势图）**。这个问题同时适用于CONSOLE-F004的预算/预测趋势图——本报告在此一并给出决策（见第9.2节Top-3），供CONSOLE-F001~F003未来复用，避免F-CONSOLE-001内部出现多套图表组件库并存的不一致局面。核查确认 `Matbox_专项21a/21b` 均未对此做过选型（已检索确认，两份报告中均未出现ECharts/Recharts/Tremor/D3/Chart.js等关键词），本报告是该决策在整个仓库范围内的首次出现。

## 6｜真实用户与开发者评价

### 6.1 Prophet 维护状态与小数据集摩擦（CONSOLE-F004重点核查对象）

- 官方文档明确定位："Prophet works best with time series that have strong seasonal effects and several seasons of historical data"——这是Prophet价值主张的前提条件，Matbox当前阶段大概率不满足。
- 维护状态："Prophet is in maintenance mode as of v1.4.0, with only bug fixes, dependency bumps... no new features are planned"（PyPI/GitHub 2026-08-15发布记录核实），不是被抛弃，但确认不会再有新能力投入。
- 真实GitHub Issue佐证小数据集摩擦：Issue #783（"Minimum number of data points in time series"，用户询问是否有最小样本量要求）、Issue #1252（"Improve predict speed on small dataset"，用户反馈小数据集下预测计算慢，根因是默认1000次蒙特卡洛模拟计算不确定性区间）——这两条都是真实、可核查的开放/历史issue，不是本报告臆测。
- **对Matbox的意义**：Prophet不是"不能用"，是"这一步投入在Matbox当前数据量级下换不来对应的准确度收益"，且软性提醒类功能不需要为了这点收益承担新增Python运行时的工程代价。

### 6.2 statsmodels 与小数据集的适配性

- 综述性评测："ARIMA (implemented via statsmodels) works well as a quick baseline... ARIMA performs well on datasets with 30–300 observations"（多篇2026年时间序列方法对比文章交叉印证，如KDnuggets/Medium综述），这个观测点区间与Matbox早期租户（月度/日度记账，运营几个月到一两年）的真实数据量级接近，理论上比Prophet更贴合。
- **对Matbox的意义**：statsmodels不是技术不行，是"要不要为一个软性提醒功能新增Python运行时依赖"这个工程决策问题——本报告的结论是现在不需要，留作监控候补（触发条件见第9.1节），不是永久排除。

### 6.3 简单移动平均/线性回归的真实局限（对采纳方案的诚实标注）

- 移动平均的真实局限："Simple Moving Average can produce lags behind the most recent data points and may miss sudden changes or turning points... gives equal weight to all observations within the moving window"（[Duke大学Robert Nau时间序列教材](https://people.duke.edu/~rnau/411avg.htm)，学术界公认的经典参考）。
- 线性回归的真实局限："Linear regression assumes a linear relationship between variables, which might not be true in more complex systems"（CFI预测方法综述）。
- **对Matbox的意义**：这些局限是真实的，本报告如实标注，不回避。但CONSOLE-F004的P0冻结规则已经明确"预测结果必须明确标注'参考预测，非承诺值'""不得触发任何自动阻断"——即产品设计本身已经承认预测不精确，只是给管理员一个大致参考，这与移动平均/线性回归"简单但有偏差"的特性是匹配的，不需要用更复杂的模型掩盖这个本来就被产品定位接受的不确定性。

### 6.4 Apache ECharts 真实评价

- 规模与治理："Apache ECharts is free under the Apache 2.0 license and has 60,000+ GitHub stars... 66.8k GitHub stars"（[LightningChart 2026对比](https://lightningchart.com/blog/best-apache-echarts-alternative-in-2026/)），Apache软件基金会顶级项目，治理结构成熟。
- 真实优势："ECharts has a genuinely broad chart type library including heatmaps, tree charts, sankey diagrams, calendar charts, geographic maps... much of which is included free versus Highcharts' add-on model"——五支柱健康度网格/预算仪表盘（gauge）/告警热力图这类Control Tower需要的图表类型，ECharts开箱即有。
- 真实局限（如实标注）："With aggressive tree-shaking, ECharts' option-object surface area carries weight that isn't fully recovered, making it problematic for bundle budgets below ~150 KB gzipped... ECharts ships at 359 KB"；"Canvas CPU rendering becomes a bottleneck with datasets consistently pushing past 500K–1M data points"（[ApexCharts 2026行业综述](https://apexcharts.com/blog/state-of-javascript-charting-2026/)）——这两条局限在Control Tower的实际数据量级（五支柱摘要指标，量级是几十到几百个数据点，不是百万级）下都不构成真实问题，如实记录但不改变结论。

### 6.5 Recharts 真实评价

- 采用规模："48.9M weekly npm downloads, the highest of any React chart library... still the practical default for many React dashboards because its component API is simple and widely understood"（[LogRocket 2026](https://blog.logrocket.com/best-react-chart-libraries-2026/)）。
- 真实局限（GitHub Issue核实，如实标注）：Bundle体积多次被开发者报告为问题（Issue #3697/#1417/#2174/#7018，均为真实存在的开放/历史issue）；大数据集下的性能问题真实存在（Issue #1146"Recharts is slow with large data"、Discussion #3181反馈散点图超过约1万个点浏览器会崩溃）。
- **对Matbox的意义**：这些局限同样在Control Tower/成本中心的实际数据量级下不构成问题（趋势图是几十个时间点，不是万级散点），Recharts的"组件API简单"这一优势对CONSOLE-F004的简单趋势/预算进度图（折线图、柱状图、进度条）是合适的选择。

### 6.6 Tremor 真实评价

- 定位："Tremor is a modern dashboard component library built on top of Recharts, ideal for interactive admin dashboards with pre-styled and responsive chart components"（[FusionCharts 2026对比](https://www.fusioncharts.com/blog/best-react-chart-library/)）。
- **对Matbox的意义**：Tremor本质是Recharts之上的样式封装层，继承Recharts的图表类型上限（无原生gauge/heatmap），且多一层需要独立跟踪版本兼容性的依赖。作为"快速做出SaaS管理台观感"的UI加速工具，可以在Stage 10前端施工阶段按需引入个别组件（如KPI卡片），但不作为核心图表引擎的选型对象。

### 6.7 Grafana嵌入商业产品的真实License约束

- "Since 2021, Grafana has been licensed under AGPLv3... If you embed Grafana into a customer-facing SaaS product, you must procure a commercial enterprise license from Grafana Labs to protect your proprietary code"（[Grafana Labs社区论坛官方回复](https://community.grafana.com/t/using-grafana-oss-embedding-in-a-commercial-saas-application/161719)、[Grafana Labs License Agreement](https://grafana.com/legal/grafana-labs-license/)交叉印证）。
- **对Matbox的意义**：这是与`专项01`对TruffleHog、`专项21a`对StaffDeck同一性质的AGPL网络著佐权风险，且这次是"嵌入到自己的商业产品UI里"这个具体场景被Grafana Labs官方明确要求要么开源自己的修改要么购买商业License——直接构成否决理由，不需要进一步比较功能。

## 9｜候选方案对比及淘汰原因（含前三名排名+理由）

### 9.1 CONSOLE-F004 成本预测方法 Top-3（回填第3.2节详表）

| 排名 | 候选 | 排名理由 |
|---|---|---|
| **#1 Matbox自研（移动平均+线性回归趋势外推）** | 零新增依赖，可解释性最强，与"参考预测非承诺值"产品定位精确匹配 |
| **#2 statsmodels（ARIMA/指数平滑）** | 技术路线成熟，适合Matbox早期数据量级，但需新增Python运行时，列为监控候补 |
| **#3 Prophet** | MIT+Meta维护，但处于维护模式+需要多季节历史数据+真实小数据集摩擦证据，过度工程 |
| 落选 | OpenCost/Kubecost | 品类不匹配（成本分摊非预测），见第3.3节 |

**#2 statsmodels 触发条件（本报告新增，避免"监控候补"变成空话）**：满足以下任一条件时应重新评估引入statsmodels：(1) Stage 10真实运营满12个月以上、单租户日度数据点稳定超过300个；(2) 有租户明确反馈简单趋势外推的预测偏差在真实场景下造成困扰（如多次出现预测值与实际值偏差超过50%）；(3) Matbox后端技术栈本身因其他原因（如AI推理相关服务）已经引入Python运行时，边际成本归零。三个条件均未满足前，不启动重新评估。

### 9.2 CONSOLE-F005（及CONSOLE-F004趋势图共用）前端图表组件库 Top-3

| 排名 | 候选 | 排名理由 |
|---|---|---|
| **#1 Apache ECharts**（经`echarts-for-react`等React封装接入） | 唯一原生覆盖"五支柱健康度网格/预算进度仪表盘（gauge）/告警热力图"这类Control Tower特有图表类型的候选；Apache-2.0清晰，ASF治理成熟度是长期信号 |
| **#2 Recharts** | 组件API最简单、生态采用率最高，承担CONSOLE-F004的简单趋势/柱状图，与ECharts按图表类型分工使用，不是二选一排他关系 |
| **#3 Tremor** | 预制仪表盘组件加速UI搭建，但继承Recharts图表类型上限，非核心引擎选型对象，Stage 10前端阶段可选局部引入 |
| 落选 | Visx | 控制力最强但开发成本最高，与Control Tower"复用已有五支柱信息架构、不需要高度定制化视觉"的实际需求不匹配 |

## 16｜鉴权、权限与多租户规范（复用F-TENANT-001既有模式）

1. **人类用户访问**：所有 `/console/cost/*`、`/console/control-tower/*` 端点要求 Bearer JWT，租户隔离遵循 `TENANT-F004`"共享表+`tenant_id`字段"模式，与`专项21a`对`TrainingFeedback`的处理方式一致。
2. **PlatformAdmin vs TenantAdmin视角区分（本报告新增，第0节修正4的具体落地）**：`GET /console/control-tower/digest`（不带tenantId）仅 PlatformAdmin 角色可调用，返回跨租户汇总视图；`GET /console/control-tower/digest/{tenantId}` 任何拥有该租户访问权限的 TenantAdmin/授权用户可调用，且鉴权层强制校验请求者身份归属的租户与路径参数一致（否则 `TENANT_BOUNDARY_VIOLATION`）。PlatformAdmin 调用带 `{tenantId}` 的端点时允许跨租户查看（用于客户支持/故障排查场景），但必须在 F-OBS-001 留下审计记录（"平台管理员查看了哪个租户的数据"本身是需要留痕的敏感操作，复用`Matbox_专项06`已定义的跨租户访问审计机制）。
3. **预算阈值配置权限**：`POST /console/cost/budget/{tenantId}/thresholds` 仅 TenantAdmin 角色可调用，修改留痕（复用COST-F002"预算规则可配置、可修改，修改留痕"验收标准）。
4. **成本预测端点无需特殊权限**：`GET /console/cost/forecast/{tenantId}` 是只读投影，任何有权访问该租户成本数据的角色均可调用，不需要额外的PlatformAdmin/TenantAdmin区分（与Control Tower不同，预测数据天然是租户私有）。
5. **五支柱下钻权限透传**：`drilldownRef`指向的具体端点（如CONSOLE-F002训练反馈详情、F-TENANT-001权限态势详情）沿用各自模块自己的鉴权规则，Control Tower聚合层不做二次权限判断，也不因为聚合层通过了鉴权就绕过下钻目标模块自己的权限校验（防止"聚合层泄露了下钻层本不该看到的数据"这类越权）。

## 17｜Provider Adapter接口规范

```yaml
CostForecastCalculator（内部逻辑，非外部Provider）:
  computeForecast(tenantId: string, employeeInstanceId: string?, windowDays: int, targetPeriod: MONTH|QUARTER) -> BudgetForecast
    # 算法：TRAILING_TREND_LINEAR
    # 1. 读取近windowDays天的cost_usage_ledger_entry，按日聚合costUsd
    # 2. 计算日均花费（简单移动平均，windowDays默认14天，可配置）
    # 3. projectedCost = 日均花费 × targetPeriod剩余天数 + 本周期已发生花费
    # 4. 数据不足windowDays天时（新租户/新AI员工）：降级为"数据不足，无法预测"而非强行外推，
    #    避免用极少样本得出误导性数字（fail-closed式的"宁可不给答案也不给错答案"）
    # 5. 未来若启用statsmodels监控候补（见9.1节触发条件），method枚举新增值，
    #    接口签名不变，只是内部实现替换，前端disclaimerText逻辑不变

ControlTowerAggregator（内部逻辑，非外部Provider）:
  aggregateDigest(scope: TENANT|PLATFORM, tenantId: string?) -> ControlTowerDigest
    # 五支柱各自的数据源查询超时应独立设置（见19节降级规范），
    # 单一支柱查询失败不应导致整个Digest请求失败，
    # 失败的支柱返回healthStatus=UNKNOWN而非整体500
```

## 18｜Webhook、回调及异步任务规范

- **成本预测无需异步/回调机制**：`GET /console/cost/forecast/{tenantId}` 是同步计算（简单移动平均+线性外推的计算量极小，无需异步化），可选缓存见第20节，缓存失效后同步重新计算，不引入消息队列。
- **Control Tower聚合摘要同样是同步只读投影**，但**五支柱各自的底层数据源查询应并发发起、独立超时**（不是串行查询5个模块再返回，避免最慢的一个支柱拖慢整个页面），实现上复用已有的异步/并发基础设施（Java后端的`CompletableFuture`并发调用5个下游客户端），不新建独立的Webhook/回调体系。
- **预算告警事件本身**（80%/100%触发提醒）已经是COST-F003的既有能力，复用F-NOTIFY-001通知通道（与`专项05`第10节一致），CONSOLE-F004不重新实现通知机制，只在预算自助视图里展示告警历史。

## 19｜错误码、重试、超时和降级规范

**完全复用** `Matbox_错误码规范_正式开发文档_V1.0-RC.md` 定义的跨模块错误码：

| 场景 | 错误码 | HTTP | 可重试 |
|---|---|---|---|
| JWT缺失/过期/签名无效 | AUTH_UNAUTHENTICATED | 401 | 否 |
| 非PlatformAdmin调用跨租户Digest端点 | AUTH_FORBIDDEN | 403 | 否 |
| 请求tenantId与用户所属租户不一致（非PlatformAdmin） | TENANT_BOUNDARY_VIOLATION | 403 | 否 |
| 请求的tenantId/employeeInstanceId不存在 | RESOURCE_NOT_FOUND | 404 | 否 |
| 预算阈值配置格式非法（如阈值不在0-100范围） | INVALID_STATE_TRANSITION（复用，非新造码） | 409 | 否 |
| 五支柱聚合中某一支柱数据源超时 | PROVIDER_TIMEOUT（复用语义，非真实Provider但同一超时处理原则） | 504（单一支柱降级，整体请求仍200） | 是（下次请求重试） |
| 未预期的内部错误 | INTERNAL_ERROR | 500 | 是（有界） |

**降级规范**：
1. 成本预测数据不足（新租户/新AI员工历史窗口不够）**不是错误**，返回200，`projectedCost=null`，`confidenceNote="数据不足，暂无法预测"`——不强行外推给出误导性数字，这是本报告在第17节已经明确的fail-closed式处理。
2. Control Tower某一支柱数据源查询失败/超时，**不阻塞整体响应**（fail-open，因为这是展示类降级，不是安全关卡）——该支柱`healthStatus=UNKNOWN`，其余四支柱正常返回，前端明确提示"该支柱数据暂不可用"而非整页报错。这与CONSOLE-F002/F-DQ-008等安全关卡场景的fail-closed原则**刻意不同**：五支柱聚合是纯展示投影，某一支柱数据缺失不构成任何越权/安全风险，不需要为了"完整性"牺牲可用性。
3. 与之相对，**PlatformAdmin跨租户访问的审计记录写入失败必须fail-closed**（不允许因为审计写入失败就放行跨租户查看，这是与COST-F005预算检查fail-closed同一原则的安全关卡，不是展示类降级）。

## 20｜数据库及Migration设计

沿用REL-F006已确认的 **Flyway** 迁移工具。CONSOLE-F004/F005 遵循"不复制事实源"原则，**不新建任何业务事实表**，仅新增两张可选的**计算结果缓存表**（TTL过期后可安全重建，不是唯一事实源，符合原设计"BudgetForecast/聚合摘要投影计算结果，可缓存不必持久化"的定位）：

```sql
-- V1__console_cost_forecast_cache.sql（CONSOLE-F004，可选性能缓存，非事实源）
CREATE TABLE cost_forecast_cache (
    cache_key               VARCHAR(256) PRIMARY KEY,  -- tenantId + employeeInstanceId? + window的组合哈希
    tenant_id                VARCHAR(64) NOT NULL,
    employee_instance_id     UUID,
    method                    VARCHAR(32) NOT NULL DEFAULT 'TRAILING_TREND_LINEAR',
    window_days               INTEGER NOT NULL,
    projected_usage           NUMERIC(18,4),
    projected_cost             NUMERIC(18,4),
    confidence_note            TEXT,
    generated_at                TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at                  TIMESTAMPTZ NOT NULL  -- 建议TTL=1小时，避免每次请求重新扫描账本
);
CREATE INDEX idx_cost_forecast_cache_tenant ON cost_forecast_cache(tenant_id, expires_at);

-- V2__console_control_tower_digest_cache.sql（CONSOLE-F005，可选性能缓存，非事实源）
CREATE TABLE control_tower_digest_cache (
    cache_key                VARCHAR(256) PRIMARY KEY,  -- scope(TENANT|PLATFORM) + tenantId?的组合哈希
    scope                      VARCHAR(16) NOT NULL,     -- TENANT | PLATFORM
    tenant_id                  VARCHAR(64),               -- scope=PLATFORM时为NULL
    digest_payload              JSONB NOT NULL,            -- 完整ControlTowerDigest对象
    generated_at                 TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at                   TIMESTAMPTZ NOT NULL      -- 建议TTL=5分钟（比预测缓存更短，因为五支柱信息时效性要求更高）
);
CREATE INDEX idx_digest_cache_scope_tenant ON control_tower_digest_cache(scope, tenant_id, expires_at);
-- 注：两张表均为纯性能缓存，缓存丢失/过期不影响数据正确性，只影响响应延迟；
-- 不建立外键约束指向底层业务表（避免缓存表与事实表产生耦合，重建逻辑完全由应用层控制）
```

## 24｜成本、性能、并发及安全要求

- **成本**：本模块最终技术路线全部为Matbox自研+开源前端库（ECharts/Recharts为npm包，无订阅费）+复用已有Postgres基础设施，无新增订阅费用。唯一隐性成本是缓存表的存储与TTL维护，量级极小（每租户每次预测/摘要请求产生一行缓存，非账本级数据量）。
- **性能**：`GET /console/control-tower/digest*` 是P1体验路径（非AI调用前置阻断路径），要求五支柱并发查询后P95<2秒（具体阈值留到Stage 10真实部署后由Platform Owner冻结）；`GET /console/cost/forecast/{tenantId}` 计算量极小（对近14天数据做简单聚合），缓存命中时应<100ms。
- **并发**：Digest缓存的重建应做去重（同一`cache_key`短时间内多个并发请求只触发一次底层聚合查询，其余等待同一结果，避免缓存击穿放大对5个下游模块的查询压力）。
- **安全**：五支柱聚合层不做二次权限判断（第16节第5条），必须确保下钻目标端点自己的鉴权正确生效，不能因为聚合层通过了鉴权就误以为下钻数据也已经过权限校验；PlatformAdmin跨租户查看必须留痕（第16节第2条），且审计写入失败必须fail-closed（第19节）。
