## 0｜给忙碌读者的结论摘要

在深入28节之前，先回答两个最关键的问题：

**问题一：现在有没有足够证据支撑"锁定一个方案"？** 没有，也不应该锁定——但不是"偷懒不做研究"的没有，是**做完全部调研后确认"团队原有的留白判断是对的"**。核心理由不是"技术不成熟"，是"没有真实使用场景数据"：Mem0/Zep/Letta/pgvector 这些候选之间谁更适合 Matbox，答案取决于 Matbox 真实的对话量级、更新频率、查询模式（是"找相似"多还是"追问最新状态"多）——这些数字现在都不存在，任何现在拍板都是猜。这与架构原则第7条"知识库原始数据必须完整保留，具体迁移机制留到开发知识库模块时再细化"、第27条"现在按需要的规模做，但地基要搭得不用重建"的精神完全一致。

**问题二：那这份报告除了"再次确认不锁定"还有什么用？** 三个真实产出：
1. **一个现在就能做、不依赖场景数据、成本几乎为零的"firm now"建议**：把 MEM-F001 已设计的 ACL 契约做成**后端无关**的 `MemoryStore` 适配器接口，并且现在就用 Matbox 已经100%在用的 PostgreSQL + pgvector 扩展（零新增基础设施、PostgreSQL License无风险）实现一个最小参考后端，用来验证接口设计本身站不站得住——这不是"选定 pgvector 做正式记忆引擎"，是"用最便宜的方式验证契约"，真正的后端选型仍然留到有真实场景时再做（详见第10/11节）。
2. **一份Top-3+详细淘汰理由的候选排名**，供"以后真有场景"的团队直接抄作业：核心结论是 **Mem0 vs Zep(Graphiti) vs Letta vs pgvector自建 之间没有绝对赢家，胜负取决于 Matbox 最终真实需要的是"个性化偏好快速检索"还是"客户需求怎么变的时序推理"**（详见第9/10节）——本报告的调研支持 Matbox 自己此前在《AI员工能力缺口调研清单》#23 里已经初步指出的方向："Matbox的场景更接近Zep"（多月对话、需求会变），但**Zep 本身已经在2025年4月停运自托管社区版**，只剩纯SaaS的 Zep Cloud（详见第3/6/8节）——这是本次调研新发现的、原有#23条记录里没有的关键变化，直接影响"以后要不要用 Zep"这个判断，必须更新记录。
3. **一条2026年真实、但容易被误判的行业信号核实**：Anthropic 自己在 Claude Code 上已经放弃向量检索改用"agentic search"（grep式工具调用检索），这个趋势Matbox此前的调研已经记录过——本报告的核实结论是：**这个趋势成立，但只对"结构化文本/代码库"这类场景成立，不能直接套用到"数以千计客户的自然语言多月对话历史+时序推理"这个场景**，两者是不同的检索问题，不能因为Claude Code不用向量库就推断Matbox的记忆系统也不需要（详见第3.4/9.4节）——这是一条本报告认为必须写清楚、避免以后被误引用的边界。

## 1｜专项目标与功能边界

知识库/记忆系统（内部代号 KnowledgeMemory，FeatureID F-MEM-001）要解决的问题：**AI员工在与家具制造企业/品牌客户，以及室内/景观/建筑设计客户进行的跨月、需求持续演进的对话中，如何存储和检索"长期该记住什么"**。

- **管什么**（目标范围，非"已设计"）：
  1. **对话历史与知识的长期存储**——不止是"最近N轮对话"，是可以跨会话、跨月检索的记忆。
  2. **客户需求的演进追踪**——"客户三个月前要现代简约风格，两周前改成了要加入原木元素"这类"什么时候变的、变成了什么"需要能被检索和推理，不只是"最新状态是什么"。
  3. **组织级共享上下文 vs 员工级私有记忆的区分**——同一租户下多个AI员工模板/实例之间，哪些记忆应该共享（如"这个客户的公司背景"）、哪些应该隔离（如"某个AI员工自己执行任务时的中间推理草稿"）。
  4. **记忆的权限治理**（MEM-F001，已设计部分）——按tenant/project/resource的访问控制、记忆的来源可追溯、TTL过期、撤销传播。
- **不管什么**：不拥有对话本身的事实源（那是F-TASK-001 TaskRun/对话记录的职责，记忆系统只是对其做二次索引/摘要）；不拥有原始文件存储（归F-STORAGE-001，架构原则第7条已定）；不做模型路由/Provider选择（归F-PROVIDER-001）；不做"谁能不能执行某个动作"的判断（归F-TENANT-001/F-ACTION-001，记忆系统的ACL只管"能不能看到/检索到某条记忆"，不管"能不能对外部世界做动作"）；不做central路由决策（归F-ORCHESTRATOR-001，但ORCHESTRATOR的路由judgement未来可能需要查询"企业共享上下文"，是记忆系统的下游消费方之一，见第2节）。
- **两个子能力当前状态**：
  - **MEM-F001 记忆访问控制（ACL/来源/TTL/撤销传播）**——🟢已设计（来自《多端平台V3.0》文档，本报告未持有该文档全文，以下所有对MEM-F001的描述均转引自`Matbox_Feature_Register.md`第111行与`architecture_dependency_diagram.html`第837-838行的摘要记录，不臆测未写明的字段细节；这是本报告如实标注信息来源的"溯源检查"，不是回避）。
  - **MEM-F002+ 核心检索架构（向量数据库选型/Embedding流程/RAG检索链路，或其他记忆范式）**——⚪未设计，本报告不代替团队"现在拍板"，只交付评估证据（详见第10节的firm-now vs conditional-future区分）。

## 2｜Matbox架构归属

知识库/记忆系统属于架构原则第2条明确列出的**平台核心能力**之一（"记忆系统"与"知识与资产系统"并列于Provider Router、Agent Runtime、权限与租户体系、可观测性、成本控制同一档次），不是某个具体业务功能，是横切给所有AI员工用的基础设施层。

**依赖方向（入）**——记忆系统依赖：
- **F-STORAGE-001**（STORAGE-F002 "知识库原始数据落地"）——架构原则第7条的落地对象，向量化之前的原始数据必须先存进对象存储/主数据库，记忆系统的Embedding流程从这里读取源数据，不自己管文件存储。
- **F-TENANT-001**（TENANT-F003 AI员工策略授权、TENANT-F004 数据隔离）——MEM-F001的ACL判断复用同一套OPA/ABAC机制和"共享表+租户ID字段"隔离模式，不新建平行鉴权体系。
- **F-CRED-001**——若最终选型涉及任何托管SaaS（Mem0 Platform/Zep Cloud/Embedding Provider API Key），凭据一律走CRED-F001的运行时代理注入，不落明文。
- **F-COST-001**——记忆系统的Embedding生成和"事实抽取"（Mem0/Zep类方案都需要额外LLM调用做摘要/去重/时序判断）产生真实token成本，必须建独立预算线，不能算进AI员工任务本身的成本里而被隐藏（与架构原则第34条"编排器自身开销必须单独建模"是同一类问题）。
- **F-AIEMP-001**（EmployeeTemplate/EmployeeInstance）——员工级私有记忆分区需要按`employeeInstanceId`隔离，依赖这里的员工身份体系。
- **F-OBS-001**——记忆的写入/检索/撤销事件需要可追溯审计，复用EvidenceBundle模式。

**被依赖方向（出）**——依赖记忆系统的：
- **F-TASK-001**（AI任务运行时）——AI员工执行多轮任务时，需要查询"这个客户过去说过什么"，是记忆系统最直接的消费方。
- **F-ORCHESTRATOR-001**（中央编排层）——架构原则第34条已记录的真实案例（Salesforce Agentforce G2差评"数据混乱、路由受影响"）说明路由判断的准确性依赖"角色定义/任务描述够不够结构化"；企业共享上下文层（AI员工能力缺口清单#22）若未来建设，会成为编排器路由判断的辅助输入之一，但**明确边界**："Glean擅长搜索发现，不负责执行工作流"（清单#22原话）——记忆系统未来最多是编排器的**只读查询辅助**，不能替代F-TASK-001/F-ACTION-001的执行判断。
- **F-CONSOLE-001**（AI员工管理控制台）——记忆检查/审计视图的展示层，复用其Ops框架，不新建。
- **F-DELEGATION-001**——多AI员工协作场景下，Coordinator做fan-out/fan-in时可能需要读取共享记忆做上下文对齐，具体依赖细节留到真实场景出现时再定。

**架构上的关键约束（本报告新增，非既有冻结）**：MEM-F001已设计的ACL契约（tenant/project/resource维度的访问控制、来源、TTL、撤销传播）**在概念上是后端无关的**——"谁能看到哪条记忆"这个判断不应该假设记忆存在Qdrant还是Postgres还是Neo4j里。本报告第10/11节会把"确保这一点在实现时成立"列为现在就该做的唯一firm动作。

## 3｜全球方案调研结果

### 3.1 赛道分层现状（2026年真实格局）

"AI员工长期记忆"这个细分赛道在2026年比DQ专项的代码质检赛道更年轻、变化更快，行业实践分五层，而不是四层：

1. **独立记忆产品/框架**：Mem0、Zep（及其开源引擎Graphiti）、Letta（原MemGPT）、Cognee——各自有独立GitHub仓库、独立商业模式，专门解决"AI Agent怎么记住东西"这一个问题。
2. **Agent框架内置的记忆原语**：LangGraph的Checkpointer（线程内短期状态）+ Store（跨线程长期kv存储）、LangChain自己的LangMem库——**不是独立产品，是某个Agent编排框架的一部分**，只有当你的Agent Runtime本身就是LangGraph时才自然可用。Matbox的Agent Runtime是Temporal（架构原则第31条已确认保留Temporal，不换DBOS），不是LangGraph，这一层对Matbox**架构上天然不适配**，详见第9节。
3. **原始向量/图数据库**：pgvector（PostgreSQL扩展）、Qdrant、Weaviate、Milvus——这些不是"记忆产品"，是给记忆产品/自建逻辑打底的存储引擎，本身不做"什么该记、什么该忘、事实怎么去重"这类记忆语义判断。
4. **前沿实验室原生记忆能力**：Anthropic Claude Managed Agents Memory（2026年4月23日公开beta）、OpenAI ChatGPT Memory——需要认真核查"是否真的可以当基础设施用"还是"只是终端用户聊天体验"，见3.3节。
5. **GraphRAG / agentic search 两个相关但不同的方向**：GraphRAG是"整个知识库转图谱再做检索增强"的技术路线（微软主推），agentic search是"完全不用向量检索、靠工具调用做检索"（Anthropic Claude Code代表），两者都可能减少或改变Matbox对独立向量数据库的依赖程度，需要分别核查是否适用，见3.4节。

### 3.2 独立记忆产品/框架详细调研

**Mem0**（`github.com/mem0ai/mem0`）——定位"速度与个性化"。核心技术路线是从对话中抽取结构化"事实"（fact extraction），去重后存入向量/图混合存储，检索时做语义匹配+个性化排序。2026年官方博客自称在LoCoMo基准上达到92.5%、LongMemEval达到94.4%（[Mem0官方博客](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)）。**但这个数字本身有真实的自我修正历史**：2025年10月，Mem0官方在自己论文里给出的LoCoMo数字是68.5（[AI Memory Stats 2026](https://preuve.ai/blog/ai-memory-systems-statistics-2026)），到2026年官方博客又提升到92.5——同一厂商同一基准，半年内自报数字上涨约24个百分点，且**评测用的模型/评测setup在两次报告之间并不完全相同**（[Mnemoverse文档](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3)明确指出"Mem0与Zep双方2026年的最新数字用了不同模型和评测设置，不可直接对比"）——本报告按用户对Betterleaks同类问题的要求，**照实标注这是厂商自证数据的连续修正，不是独立复现的稳定结论**。

**Zep / Graphiti**（`github.com/getzep/zep` 商业产品 + `github.com/getzep/graphiti` 开源引擎）——定位"时序知识图谱"，核心主张是"事实带时间戳"：每条知识都有"什么时候成立、什么时候失效、来自哪次对话"三个维度（[Zep官方定义](https://www.getzep.com/ai-agents/temporal-knowledge-graph/)），这正好对应Matbox"客户需求随时间演进"这个真实场景的核心诉求。**2026年最重要的变化**：Zep在**2025年4月停运了自托管的Community Edition**（[Zep官方公告](https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/)），现在只剩两条路：花钱用Zep Cloud（纯SaaS），或者自己拿开源引擎Graphiti（MIT协议）配合Neo4j/FalkorDB/Kuzu自建——**后者的运维复杂度比停运前的一体化CE高得多**（[Graphiti自托管说明](https://github.com/getzep/graphiti)）。Graphiti本身发展很健康——2026年已突破2万星，贡献者来自AWS、Microsoft、FalkorDB、Neo4j等真实公司（[Zep官方博客](https://blog.getzep.com/graphiti-hits-20k-stars-mcp-server-1-0/)），且FalkorDB团队已经贡献了"单容器打包、免额外Docker编排"的简化部署方案（[FalkorDB Lite Issue #1240](https://github.com/getzep/graphiti/issues/1240)）——但截至本报告调研时点，仍然需要额外的图数据库服务，不是"装个Postgres扩展"这种零新增基础设施的方案。**Zep自己的LoCoMo基准数字也被公开挑战**：Mem0团队在复现Zep宣称的84%准确率时，用相同/对齐后的评测方法只得到58.44%（[getzep/zep-papers Issue #5](https://github.com/getzep/zep-papers/issues/5)）——这是一场双方互相质疑对方评测方法的公开争议，本报告不选边站，只如实记录"两边的自报数字都不是独立第三方定论"。

**Letta（原MemGPT）**（`github.com/letta-ai/letta`）——定位"有状态Agent操作系统"，核心设计是OS启发的三层记忆（Core Memory类比RAM/常驻上下文、Recall Memory类比磁盘缓存/可搜索历史、Archival Memory类比冷存储/工具调用式检索），本质上是**一整套Agent运行时**，不是一个可以单独插入现有Agent架构的记忆层。2026年6月快照约2.3万星（[GhTrends](https://ghtrends.dev/letta-ai/letta/)），Apache-2.0协议（[letta-code LICENSE](https://github.com/letta-ai/letta-code/blob/main/LICENSE)）。**2026年的真实信号是公司重心已经转移**：Letta团队2026年的产品中心是"Letta Code"（一个记忆优先的编程Agent，带桌面App），而不是原来的通用记忆平台本身（[Ry Walker Research](https://rywalker.com/research/letta)）——这意味着如果Matbox采用Letta做记忆层，实际上是在依赖一个"公司战略重心已经移开"的子产品线，长期维护投入的信号弱于其巅峰期。真实生产反馈也印证了这一点：**"团队从原型走向生产时，遇到框架锁定问题、纠结于自我编辑记忆的不可预测性"**（[EverMind Letta替代方案调研](https://evermind.ai/blogs/letta-alternative)），2026年3月的一次大版本更新专门修复了"上下文窗口重置"等自托管用户的严重bug（context window reset bug LET-7991），说明产品仍在快速迭代稳定期，不是成熟静态产品。

**Cognee**（`github.com/topoteretes/cognee`）——较新的挑战者，定位"图原生记忆平台"，核心是ECL（Extract-Cognify-Load）管道+14种检索模式+30多种数据源接入+可插拔存储后端，2026年已突破7000星，且已通过GitHub Secure Open Source Program认证（[Cognee官方博客](https://medium.com/@cognee/cognee-ai-memory-security-cognee-graduates-github-secure-open-source-3032d42f78a1)），Apache-2.0协议。定位上被行业评测认为"最适合本地优先、隐私敏感、需要图推理的部署场景"（[Cognee对比文章](https://cognee.ai/blog/guides/best-ai-memory-layers-for-ai-agents-in-2026-comparison)）——这个定位与Matbox"自托管优先、多租户敏感客户数据"的原则方向一致，值得列入候选，但成熟度证据（7千星 vs Mem0的4万+、Graphiti的2万）明显薄于前两者，属于"值得记录但现在证据强度不够冲进前二"的候选。

**LangMem**（LangChain生态自带库）——"LangGraph原生团队的天然默认选择"（[Cognee对比文章](https://cognee.ai/blog/guides/most-popular-memory-agents-developers)），提供核心记忆API、热路径记忆工具、后台记忆管理器，与LangGraph的Store原语深度绑定。**对Matbox不适用的原因是架构层面的，不是能力层面的**：Matbox的Agent Runtime是Temporal（架构原则31条已确认），LangMem/LangGraph Store这套记忆原语假设的是LangGraph的图执行模型和State管理机制，脱离LangGraph单独使用价值大幅降低，引入它意味着要么额外接入一套与现有Temporal编排完全不同的执行框架（架构冲突），要么只取其记忆存储的设计思路自己重写（等于没有真正复用）。

### 3.3 原始向量/图数据库层（"打底存储"层）

**pgvector**（`github.com/pgvector/pgvector`）——PostgreSQL的向量扩展，PostgreSQL License（宽松协议，近似MIT/BSD）。核心优势是"没有新服务、向量和业务数据同表存储、零新增鉴权面"（[Kalviyum Labs对比](https://www.kalviumlabs.ai/blog/vector-databases-compared-pgvector-pinecone-qdrant-weaviate/)），"对多数组织，1000万向量以内的场景，pgvector是最聪明的起点"（[buildmvpfast对比文章](https://www.buildmvpfast.com/blog/pinecone-vs-weaviate-vs-qdrant-vector-database-comparison-2026)）。**这一条对Matbox有直接的现实意义**：Matbox当前架构确认"只用PostgreSQL"（`Matbox_发布与基线系统_正式开发文档_V1.0-RC.md`第88行），这意味着pgvector是本报告调研的所有选项里**唯一"不需要新增任何一个数据库系统"**的选项——不是因为它性能最强，是因为它是Matbox已经在运维的基础设施的自然延伸。但要明确：**pgvector只是相似度检索索引，不是记忆系统**——它不做事实抽取、去重、时序失效判断、摘要合并这些Mem0/Zep/Letta做的"记忆语义"工作，选它意味着这些逻辑全部要Matbox自己写。

**Qdrant**（`github.com/qdrant/qdrant`）——Apache-2.0，Rust编写，自托管/云端均可，"过滤检索场景下延迟最强的默认选择"，p50约4ms（[综合对比文章](https://encore.dev/articles/best-vector-databases)），G2评分4.5/5（12条评价），真实好评集中在速度和文档完整度，差评集中在"缺内置可视化工具"（[G2/Qdrant对比页](https://www.g2.com/products/qdrant)）。自托管成本：千万级向量单VPS约50-100美元/月（[成本对比](https://ranksquire.com/2026/03/04/vector-database-pricing-comparison-2026/)）。

**Weaviate**（`github.com/weaviate/weaviate`）——BSD-3-Clause，内置向量化模块（可以直接喂原始文本，自动生成向量），G2评分4.6/5（29条评价，略高于Qdrant），但存在真实的严重故障报告：**"曾遇到数据损坏，Weaviate完全不可用，每次请求返回不同数据，客服每次响应要一天"**（[G2 Weaviate vs Qdrant对比页](https://www.g2.com/compare/qdrant-vs-weaviate)）——这是本报告认为值得记录的真实负面证据，不能因为整体评分略高就忽略这条具体故障报告。

**Milvus**（`github.com/milvus-io/milvus`）——Apache-2.0，**LF AI & Data Foundation的毕业级项目**（Graduate Level，需要"持续多组织贡献+成熟治理结构"才能达到，[LF AI官方公告](https://lfaidata.foundation/blog/2021/06/23/lf-ai-data-foundation-announces-graduation-of-milvus-project/)），治理成熟度是本次调研四个向量库里最强的（不依赖单一商业公司）。但"运维复杂度明显超过同规模场景下的Qdrant"（[pistack.xyz对比](https://www.pistack.xyz/posts/)），更适合1亿+向量规模的场景，对Matbox当前"2人团队、真实场景未知"的规模明显是过度设计。

### 3.4 GraphRAG 与 "Agentic Search替代向量库" 两个趋势的正面核查

**GraphRAG（微软）现状**：`microsoft/graphrag`项目**已进入维护模式，不再接受新PR/新功能，只做bug修复和CVE相关的依赖更新**（[GraphRAG GitHub Issues](https://github.com/microsoft/graphrag/issues)）。真实成本证据："一个不到5美元就能做向量Embedding的语料库，用GraphRAG的实体抽取+社区摘要管道要花50-200美元"，"对1万篇文档规模的知识库，索引成本可以到四位数美元，大数据集甚至到过3.3万美元"（[Graph RAG 2026实践指南](https://medium.com/graph-praxis/graph-rag-in-2026-a-practitioners-guide-to-what-actually-works-dca4962e7517)）。真实负面反馈："GraphRAG让大多数查询变得更差，它是为一种特定问题设计的，用它处理其余类型的问题是常见的错误"（同上）。**结论**：GraphRAG（微软这个具体实现路线：全量实体抽取+社区摘要）成本/收益比对Matbox不合适，予以排除；但这**不等于**"图结构对Matbox的记忆场景没用"——Graphiti（3.2节）走的是完全不同的技术路线（增量式时序事实图，不做全量社区摘要），不应该把GraphRAG的负面结论错误地套用到Graphiti头上，这是本报告要求特别澄清的一点。

**"Agentic Search让Agent不再需要向量库"是否适用于Matbox的记忆场景**：这是Matbox此前调研（架构原则确认的行业前沿追踪要求）已经提到的真实趋势，核实结论如下——2025年5月，Anthropic把Claude Code里的向量检索（Embedding管道+本地向量库+分块逻辑）整体移除，换成基于grep的"agentic search"，Claude Code创造者Boris Cherny的原话是"效果好很多，而且更简单，没有向量检索在安全性/隐私/陈旧度/可靠性上的那些问题"（[Anthropic Replaced Their RAG Pipeline](https://robertheubanks.substack.com/p/anthropic-replaced-their-rag-pipeline)）；2026年2月Amazon Science的论文进一步验证"基于工具调用的关键词检索能达到RAG检索效果的90%以上，且不需要向量数据库"（同上）；Cursor、Windsurf、Cline、Devin、Sourcegraph Amp等一批同类产品跟进放弃向量检索。**但本报告核实后认为这个趋势不能直接套用到Matbox的核心记忆场景上，原因是两类检索问题的本质不同**：
- Claude Code的场景是"在一个结构良好、可被grep穷举匹配的**代码库/文本仓库**里找到相关文件"——代码有精确的符号名、导入关系、目录结构，关键词/正则天然命中率高。
- Matbox要解决的是"在成百上千个客户、跨月的**自然语言对话历史**里，判断某条模糊表达的新需求是否与三个月前某次对话里的某个旧偏好相关，以及这个偏好后来有没有被更新过"——这类语义相似度匹配+时序推理，天然不是关键词能覆盖的问题，这也是LoCoMo/LongMemEval这类记忆基准存在的原因（专门测"多跳语义关联+时序推理"，不是测"关键词命中率"）。
- **结论**：Matbox未来若真的建设记忆系统，"agentic search能不能减少某些子场景对向量库的依赖"这个问题值得保留——比如"查找某个客户过去上传过的产品规格文档"这种偏结构化检索，agentic search（对F-STORAGE-001里已有元数据做工具调用式查询）确实可能比建一整套向量索引更划算；但"追踪需求怎么演变"这类核心场景，现有证据不支持完全放弃语义检索/时序建模能力。这是一个**部分适用**的结论，不是"全有或全无"，本报告要求以后任何人引用这条趋势时保留这个边界，不能简化成"Claude Code不用向量库所以Matbox也不用"。

### 3.5 前沿实验室原生记忆能力：能否当基础设施用

**Anthropic Claude Managed Agents Memory**——2026年4月23日公开beta，是给"Claude Managed Agents"（Anthropic托管的Agent运行时）用的文件式记忆工具，Claude可以自己创建/读取/更新/删除记忆目录里的文件，配合Context Editing自动清理过期的工具调用结果（[Anthropic官方博客](https://claude.com/blog/claude-managed-agents-memory)）。真实早期采用方包括Netflix、Rakuten、Wisedocs、Ando，内部基准显示100轮网页搜索任务上token节省84%、效果提升39%（同上）。**能否作为Matbox基础设施**：技术上可用，但**与架构原则第2条"不绑定单一供应商/模型"直接冲突**——这个记忆工具是"Claude Managed Agents"这个Anthropic托管执行环境的能力，记忆数据的存储位置/格式由Anthropic托管基础设施决定，如果Matbox的Provider Router以后把某个AI员工的模型换成非Claude供应商，这部分记忆不会自动跟着搬迁。**结论**：不采纳为核心记忆基础设施，但可以作为"某个具体AI员工模板如果被配置为强绑定Claude Managed Agents执行"时的**局部、可选**能力观察，不影响整体记忆系统架构判断。

**OpenAI ChatGPT Memory**——2026年6月已重构升级（[OpenAI官方博客](https://openai.com/index/chatgpt-memory-dreaming/)），但**明确不通过API对开发者开放**，"这个记忆功能只在OpenAI自己的App里，不通过API"（[OpenAI Developer Community讨论](https://community.openai.com/t/backend-memory-api-availability/1327871)）。**结论**：直接排除，不构成Matbox可用的基础设施选项，这是本次调研里少数"证据非常干净、不需要进一步权衡"的排除结论之一。

## 6｜真实用户与开发者评价

### 6.1 Mem0
- Hacker News真实讨论（2026-02-10）："Mem0存储对话中的事实，但不会隐式地从行为模式中学习用户习惯"（[HN讨论](https://news.ycombinator.com/item?id=46891715)）——指出的是Mem0的核心技术路线局限：擅长"记住说过的话"，不擅长"从长期行为里总结出未明说的偏好"。
- 自报基准数字半年内从68.5大幅上调到92.5（见3.2节），需按用户对Betterleaks同类情况的要求标注为"厂商自证、非独立复现"。

### 6.2 Zep / Graphiti
- Zep自己2026年宣称LoCoMo准确率84%，被Mem0团队在对齐评测方法后复现为58.44%（[getzep/zep-papers Issue #5](https://github.com/getzep/zep-papers/issues/5)），是一场双方互相指出对方方法论问题的公开争议，本报告不采信任一方的单方面数字。
- Graphiti本身作为开源引擎的评价整体正面，真实生产采用方包括企业级图数据库厂商（FalkorDB/Neo4j）直接贡献代码，是"专业图数据库厂商愿意投入维护"的真实信号，与DQ报告里"Aikido底层用OpenGrep"是同一类型的可信证据。

### 6.3 Letta
- 真实生产反馈两极："能自主处理有状态的多轮任务"（正面）vs**"团队从原型走向生产时,遇到框架锁定问题,纠结于自我编辑记忆的不可预测性,主动寻找Letta的替代方案"**（[EverMind调研](https://evermind.ai/blogs/letta-alternative)，非厂商自己的话）。
- 2026年3月的版本记录显示专门修复了自托管用户的上下文窗口重置bug（LET-7991）并"大改"了压缩逻辑（[Letta Releases](https://github.com/letta-ai/letta/releases)）——说明核心记忆机制在2026年仍在经历架构级修正，不是已经沉淀稳定的成熟系统。

### 6.4 pgvector / Qdrant / Weaviate / Milvus

### 9.3 "整体买一个企业共享上下文/知识管理平台"的正面核查（方法论第2条）

参照《AI员工能力缺口调研清单》#22已完成的初步核查：**Glean**（企业级权限感知知识图谱/搜索平台）G2真实评分4.7/5（145条评价），正面"一周省好几小时、权限系统好、无泄露"，差评"贵、大公司部署麻烦、聊天会幻觉"，**关键边界**是官方自己承认"Glean擅长搜索发现，不负责执行工作流"。本报告核实结论：Glean类平台解决的是"企业内部文档/知识搜索"，与Matbox需要的"AI员工与单个客户的多月对话记忆+需求演进追踪"是不同的问题（前者是"企业内部资料库"，后者是"AI员工的对话记忆"），**不构成对F-MEM-001核心检索架构的整体替代**，最多是未来"企业共享上下文层"这个相邻但不同的能力（清单#22）的候选，两件事不应该混为一谈。

### 9.4 关于"agentic search能否让Matbox不需要向量数据库"的最终结论

见3.4节详细论证，结论重申：**部分适用，非全部适用**。对F-STORAGE-001里已有结构化元数据的检索（如"查这个客户上传过的某类文档"），agentic search式的工具调用检索值得作为轻量起点评估；对核心的"多月对话语义关联+时序推理"场景，现有证据不支持完全放弃语义检索能力。这个结论应该被记录进以后任何真实场景设计时的评估依据，不能被简化引用。

## 10｜最终技术路线与选择依据

**本节是本报告与DQ模板报告结构性最大的不同点，必须先说明体例**：DQ报告第10节给出的是"每个FeatureID的最终路线"（因为DQ的13个子能力都已有明确场景）；本专项因为核心检索架构⚪尚未设计、且团队自己的原则是"没有真实场景不锁定"，所以第10节分两部分回答：

### 10.1 现在（无真实场景）就该做的事——firm now

1. **把MEM-F001已设计的ACL契约做成后端无关的设计**——检查（并在真实施工时强制要求）MEM-F001的记忆访问控制判断只依赖抽象的`resourceRef`/`tenantId`/`ttl`/`sourceRef`等字段，不引用任何具体后端（Qdrant的collection、Mem0的memory_id、Neo4j的node label等）的原生结构。这是本报告唯一要求"现在就做"的架构约束，成本几乎为零（只是设计纪律，不是新增开发工作量）。
2. **定义一个`MemoryStore`适配器接口**（第17节给出具体契约草案），任何未来选定的后端（pgvector/Mem0/Graphiti/Qdrant等）都通过实现这个接口接入，不让具体后端的SDK/schema泄漏进Matbox领域模型——与DQ报告"Own/Reuse/Must Not Rebuild"原则的`ScannerAdapter`模式是同一思路的复用。
3. **用pgvector做一个最小参考实现，只为验证接口设计，不是选定生产后端**——因为Matbox已100%使用PostgreSQL，加一个pgvector扩展是zero-新增基础设施、零许可证风险的动作,可以用来跑通"AI员工写入一条记忆→按ACL检索→按TTL过期"这个最小闭环，验证MEM-F001的契约设计是否真的经得起实现,而不需要现在就决定"pgvector是不是最终答案"。**这不是"选型"，是"用最便宜的方式验证设计"。**
4. **不做的事**：不选定Mem0/Zep/Letta/Graphiti中任何一个作为生产记忆引擎；不现在就为Embedding流程/RAG检索链路做详细API/Schema设计（那些设计依赖"记忆量级、查询模式"这些现在不存在的真实数据，现在设计等于猜测，猜错了比不设计更浪费）；不因为本报告存在就误以为"记忆系统已经选型完成"（与Feature Register现有标注的精神一致，本报告需要在完成后同步更新该行的说明）。

### 10.2 若/当真实场景到达——证据支撑的候选排序（非现在的决定）

基于第9节的完整排名，给出一条**有条件的路线图**，供真实场景数据出现时直接参考，而不是从零开始：

- **如果真实数据显示"客户需求的时序演进追踪"是高频、高价值场景**（与Matbox当前对自身业务的描述一致）：优先评估**基于Graphiti自托管二次开发**——这不是"直接引用"（因为Graphiti是引擎不是成品，且需要额外的图数据库运维投入），是"基于开源项目二次开发"，理由见9.1节。
- **如果真实数据显示"起步阶段量级小、优先降低运维复杂度、想尽快有个能跑的版本"**：优先评估**Mem0开源库自托管**，且可以尝试把Mem0的向量存储后端直接指向Matbox已有的pgvector，兼顾"接入成熟记忆语义逻辑"和"不新增独立向量数据库系统"两个目标。
- **如果真实数据显示"记忆需求其实很轻量，大部分是结构化检索，语义/时序诉求不强"**：可能根本不需要Mem0/Zep/Letta这类重量级方案，直接在pgvector之上写Matbox自己的轻量检索逻辑（甚至评估3.4节讨论的agentic search式检索）就够，避免过度设计。
- **任何情况下都不建议**：Zep Cloud（SaaS-only+中国可达性未知+停运自托管CE三重风险叠加）、Letta（架构与Temporal Agent Runtime冲突）、LangMem（架构与Temporal Agent Runtime不匹配）、Claude Managed Agents Memory作为核心基础设施（供应商锁定，冲突架构原则第2条）、Microsoft GraphRAG全量路线（成本不成比例）。

## 11｜自研、复用、二开和采购的边界

- **OWN（Matbox必须自己拥有）**：MEM-F001的ACL/TTL/撤销传播判断逻辑；`MemoryStore`适配器接口本身；无论最终选哪个后端，"AI员工私有记忆 vs 组织共享记忆"的分区规则；记忆写入的成本预算控制逻辑（对接F-COST-001）。
- **REUSE（引用其他专项，不复制）**：F-STORAGE-001的原始数据落地（架构原则第7条）；F-TENANT-001的鉴权/ABAC判断机制；F-CRED-001的凭据代理注入（若涉及任何外部API Key）；F-OBS-001的审计证据链；F-AIEMP-001的员工身份体系。
- **MUST NOT REBUILD（禁止重新发明）**：向量索引算法本身（HNSW等，不管选pgvector/Qdrant/Milvus哪个，都不自己写索引引擎）；图数据库存储引擎本身（若走Graphiti路线，不自己写图存储，只写Matbox领域适配层）；Embedding模型本身（复用Provider Router接入的模型能力，不自己训练）。
- **二开候选（非现在拍板，留待真实场景）**：Graphiti自托管——若选择这条路线，二次开发的是"Matbox领域的事实抽取prompt/schema+MEM-F001 ACL集成层"，不是重写Graphiti引擎本身。
- **采购（已评估并明确不采纳，非"还没决定"）**：Mem0 Platform、Zep Cloud、Claude Managed Agents Memory 三者均因SaaS-only/中国可达性/供应商锁定风险被排除为核心基础设施采购路径，见第9/10节。

## 16｜鉴权、权限与多租户规范（复用F-TENANT-001既有模式）

与DQ报告第16节完全同构，不新建平行体系：

1. **人类用户访问**：复用`POST /tenant/sessions`的JWT（携带tenantId claim），角色沿用TENANT-F002已定义的7个具名角色。
2. **AI员工访问**：AI员工查询/写入记忆前，必须先经`GET /cred/agent-grants`（CRED-F003）领取范围内的短期Token，记忆系统内部调用`POST /tenant/authz/check`做ABAC判断，`resource_type=memory_record`，`action=read|write|forget`；权限范围不得超过当前任务/委派链所属的scope（EMPLOYEE_PRIVATE不可越权读取其他员工实例的私有记忆，除非明确走ORG_SHARED）。
3. **多租户隔离**：所有记忆表强制`tenant_id`字段，遵循TENANT-F004模式，查询层禁止绕过租户过滤。
4. **PlatformAdmin访问**：必须走TENANT-F002定义的break-glass流程（时限+理由+不可篡改审计）——记忆内容可能包含客户敏感商业信息（如未公开的产品需求），比DQ模块的Finding代码片段更敏感，这条规则的执行力度应不低于DQ模块。
5. **凭据**：若最终选型涉及任何外部Embedding Provider API Key，一律走CRED-F001运行时代理注入。

```sql
-- V1__mem_reference_impl.sql（仅供验证MemoryStore接口设计，非最终生产schema）

CREATE EXTENSION IF NOT EXISTS vector;  -- pgvector扩展，PostgreSQL License

CREATE TABLE mem_memory_record (
    memory_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL,
    scope VARCHAR(32) NOT NULL, -- EMPLOYEE_PRIVATE|ORG_SHARED|PROJECT_SCOPED
    owner_employee_instance_id VARCHAR(64),
    content TEXT NOT NULL,
    source_ref VARCHAR(128) NOT NULL, -- 指向F-STORAGE-001原始数据，架构原则第7条
    embedding VECTOR(1536),  -- 维度依所选Embedding模型而定，占位值
    valid_from TIMESTAMPTZ NOT NULL DEFAULT now(),
    valid_until TIMESTAMPTZ,  -- null=仍然生效；本参考实现不做自动时序失效推理，
                              -- 仅保留字段占位，真正的时序推理是Graphiti类后端的核心能力
    supersedes_memory_id UUID REFERENCES mem_memory_record(memory_id),
    ttl_expires_at TIMESTAMPTZ,
    revoked_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_mem_tenant ON mem_memory_record(tenant_id);
CREATE INDEX idx_mem_scope ON mem_memory_record(tenant_id, scope, owner_employee_instance_id);
-- HNSW索引，pgvector 0.7+支持，具体参数需按真实Embedding维度/量级调优，现在不虚构阈值
CREATE INDEX idx_mem_embedding ON mem_memory_record USING hnsw (embedding vector_cosine_ops);

CREATE TABLE mem_acl (
    acl_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL,
    memory_id UUID NOT NULL REFERENCES mem_memory_record(memory_id),
    -- 以下字段结构引自Feature Register对MEM-F001的摘要描述（ACL/来源/TTL/撤销传播），
    -- 完整字段定义需要以未来获得的《多端平台V3.0》原文核实为准，本报告不臆测细节
    principal_type VARCHAR(32) NOT NULL, -- tenant|project|resource
    principal_ref VARCHAR(128) NOT NULL,
    granted_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at TIMESTAMPTZ,
    revocation_reason TEXT
);
CREATE INDEX idx_mem_acl_memory ON mem_acl(memory_id);
```

**重要限制声明**：以上schema是"验证MemoryStore接口能否落地"的最小实现，**不是生产级记忆系统的数据库设计**——真正的生产设计必须等真实场景确定后端选型后重新做（若选Graphiti，主存储会是图数据库而非此表结构；若选Mem0自托管，需要对齐其自身的存储契约）。

## 28｜交给未来AI开发人员的完整执行说明

如果你是接手这个模块的未来AI开发者（Codex或其他），请按以下顺序理解和执行：

1. **先确认这个模块的真实状态**：核对`Matbox_Feature_Register.md`第111行、`Matbox_架构设计原则.md`第7条，确认F-MEM-001是否仍然是"仅ACL已设计、核心检索架构未设计"这个状态——如果你看到这份状态发生了变化（比如团队已经拿到真实场景数据并做了选型），说明本报告的第10.2节需要被激活执行，而不是继续停留在"不锁定"。
2. **不要重新做的事**：不要重新调研Mem0/Zep/Letta/pgvector的基本事实（License、GitHub规模、基准benchmark、真实差评）——第3-9节已经做过，除非你发现这些证据已经过时（比如Zep又重新推出了自托管CE，或者Mem0基准数字又有新的独立复现结果），要用新证据更新而不是从零来过。
3. **可以现在做、不需要等场景数据的事**：第10.1/17/20/21/23节的firm-now部分——`MemoryStore`接口定义、pgvector参考实现、MEM-F001 backend-agnostic校验。这些不依赖真实场景，随时可以排期。
4. **绝对不要做的事**：不要因为"报告已经把候选都列出来了"就自己拍板选一个后端进入生产——本报告的核心结论是"证据收集完了，但选型判断依赖真实场景数据，这个数据现在不存在"，跳过这一步等于重犯"没有真实使用场景就锁定方案"这个团队已经明确要求避免的错误（架构原则第7/31条精神）。
5. **如果真实场景数据出现了，你的任务是**：回到第10.2节，看真实数据落在哪个分支（时序演进为主/起步轻量为主/结构化检索为主），选定对应路线，然后**才**开始第12-27节标注为"条件性"的那些设计工作——那些草案是给你一个起点，不是可以直接照抄进生产的冻结契约，必须结合真实数据重新校准（尤其是第20节的schema、第24节的性能阈值）。
6. **发现本报告的信息来源局限时**：第26节已经如实标注"MEM-F001完整字段定义未在本地留存"，如果你能拿到《Matbox_多端平台_CURRENT_正式开发文档_V3.0》原文，请核对本报告第14/17/20节里所有标注"引自Feature Register摘要"的字段定义，如有出入以原文为准并更新本报告。
