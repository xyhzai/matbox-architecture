## 0｜给忙碌读者的结论摘要

在深入28节之前，先直接回答用户最关心的问题：**"训练中心"到底是不是真的自研没得选，还是因为没做过真候选对比才默认自研？**

**核查结论：这次真的没得选（可核查、非默认结论），但原设计存在两处此前未被发现的设计缺口，本报告要求修正：**

1. **"AI员工训练"这个词本身的含义先被核实、非假设正确**——Matbox 通过 F-PROVIDER-001 调用 Claude/GPT/Gemini 等闭源前沿模型的 API，不拥有、也不修改任何模型权重。核对 `Matbox_AI员工身份_正式开发文档_V1.0-RC.md` AIEMP-F001 后确认：CONSOLE-F002 的"训练"实际改的是 `EmployeeTemplate`/`EmployeeInstance` 存储的 `role_code/business_goal/responsibilities/forbidden_actions/skills[]/sop_ref/kpi_profile/quality_profile/budget_policy/permission_policy` 这些结构化字段，经 AIEMP-F004 版本审计后生效——这不是字面意义的模型微调（fine-tuning/RLHF weight update），是"业务人员纠错 → 结构化配置差异（diff）→ 审计留痕 → 下次调用读取新配置"这条反馈回路。本报告第2/3节对这条理解做了独立验证，不是照抄任务描述。
2. **真实存在且专门解决"人纠正AI输出、形成可追溯反馈"这个问题的开源品类是"人工标注/反馈平台"（Argilla、Label Studio），本报告对两者都做了深度核查，结论是：概念上最贴合的 Argilla 反而在维护状态上出现了本报告最重要的一条新证据**——Argilla 官方仓库当前显式声明"原作者团队已经转向其他项目，不再添加新功能，只做bug修复，正在寻找新维护者接手"（GitHub README实时核实，见第6.1节），且可查的提交历史在2025年3月后基本停滞。这正是用户强调的"不是有星就行，要看真实的评价"的典型案例——Argilla 有 5.1k star、Apache-2.0、Hugging Face 背书，星数和license都不差，但真实维护状态是事实上的"孤儿项目"，不能作为 Matbox 生产依赖引入。Label Studio（28.2k star，HumanSignal，Apache-2.0）维护活跃，但定位是通用多模态标注工具，不理解 Matbox 的三层Schema。**两者都不采纳为基础设施，但两者的交互模式（标注队列、评分维度、键盘驱动审核）值得作为 Matbox 自研UI的设计参考，本报告在第9/10节给出这个"参考但不引入代码"的中间结论，不是简单的"自研"两个字。**
3. **RLHF-as-a-service（模型厂商官方"喂反馈直接调模型"的API）2026年现状是"在收缩，不是在成熟"**——这是原设计完全没有查证过的一层，本报告新增：Anthropic 至今没有公开的 Claude 微调 API（仅企业定制协议，非自助）；OpenAI 已经在**收缩**其微调平台（"OpenAI is winding down the fine-tuning platform... no longer accessible to new users"），其强化微调（RFT）目前只支持 `o4-mini` 一个推理模型；Google Vertex AI 的 RLHF 是真实存在的托管服务，但只服务 Google 自己的 Gemini/PaLM 系列模型。三家没有一家提供"多租户、多供应商统一喂反馈"的能力，与 Matbox 的 F-PROVIDER-001（多Provider路由架构）天然不兼容。**结论：这一层现状不改变"Matbox必须自己做配置层反馈回路"的判断，反而进一步印证了这个判断——如果哪天某家模型厂商真的做出多租户/多模型通用的反馈API，那时候Matbox能替换的也只是"字段生效"这一步，不能替换"业务人员在哪个字段上纠错"这个Matbox专属的领域建模。**
4. **原设计遗漏的一条真实业务规则缺口（本报告新增，非用户任务描述中已提到的内容）**：CONSOLE-F002 原设计的 `TrainingFeedback.feedbackType` 分为 `BEHAVIOR_CORRECTION`/`POLICY_ADJUST_REQUEST` 两类，但没有明确写清楚"这两类反馈最终写到哪一层"。核对 AIEMP-F001/F002 后发现：`EmployeeTemplate` 是**跨租户共享的岗位库资产**，只有 PlatformAdmin 能发布/修改；`EmployeeInstance` 才是**租户私有的覆盖层**，且 AIEMP-F002 已经有明文不可变原则"不允许扩大平台禁止权限"。这意味着：`BEHAVIOR_CORRECTION`（业务人员日常纠错，如"这类退换货问题应该这样答复"）合法写入点应该是 `EmployeeInstance` 的租户覆盖字段，走轻量审核；但 `POLICY_ADJUST_REQUEST`（业务人员要求放宽某个禁止动作/权限边界）**无论走不走 F-APPROVAL-001 审批，都不能被允许直接突破 Template 定义的平台级 `forbidden_actions` 边界**——这类请求批准后的真实落点应该是"生成一条 Template 变更提案，转交 Template Owner/PlatformAdmin 走 AIEMP-F001 的模板版本发布流程"，而不是被 CONSOLE-F002 自己悄悄在 Instance 层"批准通过"。原设计文档没有把这条边界写清楚，本报告在第6/10/11节把它列为**新增 P0 冻结规则**，防止未来实现时出现"业务人员的审批意外突破了平台护栏"这个真实的安全缺口。

其余部分（反馈提交表单、状态查询、证据链关联）经核查确认原设计方向正确，只是缺少与 AIEMP-F004 已经确定的 RFC 6902 JSON Patch diff 格式对齐（见第14节），本报告一并补齐。

## 1｜专项目标与功能边界

AI员工训练中心（内部代号 Training Center，CONSOLE-F002）解决的问题：**一个不懂技术的业务人员，在租户公司里发现某个AI员工上次的产出/处理方式不对，想让它以后按正确方式来做，而且这个"纠正"必须留痕、可追溯、不能被静默应用。**

- **管什么**：业务人员对某个 `EmployeeInstance` 提交结构化修正反馈；反馈自动/半自动分类（是"日常行为纠偏"还是"权限/策略调整请求"）；反馈映射为对 `EmployeeInstance`（必要时提议 `EmployeeTemplate`）具体字段的差异（diff）草案；根据反馈类型走轻量审核或 F-APPROVAL-001 正式审批；生效后写入 AIEMP-F004 配置版本审计；反馈历史与生效状态可查询、可下钻到原始被纠正的AI输出证据。
- **不管什么**：不做模型权重级微调/RLHF训练（Matbox不拥有模型权重，见第0/3节）；不重新存储 `EmployeeTemplate`/`EmployeeInstance` 的事实数据（唯一事实源仍是 AIEMP-F001/F002，本模块只产出并应用"变更提案"）；不自建第二套审批引擎（policy-level变更走已建成的 F-APPROVAL-001）；不自建第二套审计存储（写入 F-OBS-001/AIEMP-F004 既有审计事实源）。
- **在架构中的位置**：CONSOLE-F002 是 F-CONSOLE-001（AI员工管理控制台）5个Feature之一，直接依赖 AIEMP-F004（配置版本与审计）作为反馈生效的唯一合法通道，涉及权限边界扩大的请求还要经过 F-APPROVAL-001；本身不拥有 `EmployeeTemplate`/`EmployeeInstance` 的事实源，只拥有新增的 `TrainingFeedback` 实体。

## 2｜Matbox架构归属

CONSOLE-F002 属于 **面向租户管理员的第一方产品体验层**（F-CONSOLE-001域），是 AIEMP-F004 之上的一层**业务编排 + 用户体验**，不是独立的技术基础设施。

**依赖方向（入）**——CONSOLE-F002 依赖：
- AIEMP-F001（EmployeeTemplate Registry，读取当前模板定义的 `forbidden_actions`/`permission_policy` 作为校验上界，不允许生成越界的diff草案）
- AIEMP-F002（EmployeeInstance，`BEHAVIOR_CORRECTION`类反馈的合法写入目标）
- AIEMP-F004（配置版本与审计，diff格式**复用**已经确定的 RFC 6902 JSON Patch 标准，见 `Matbox_专项15_AI员工身份_技术选型与开发交接报告_2026-08-30.md` 第9/11节——本报告不新造一套diff协议）
- F-APPROVAL-001（`POLICY_ADJUST_REQUEST` 类反馈的审批通道，本身是 Temporal+OPA 状态机，见 `Matbox_专项17_AI动作审批_技术选型与开发交接报告_2026-08-30.md`）
- F-OBS-001（原始被纠正AI输出的证据链来源，`TrainingFeedback` 必须能下钻到具体 `evidenceBundleRef`/`traceId`，不允许"凭空"提交反馈）
- F-TENANT-001（鉴权与多租户隔离，复用既有 ABAC 模式，见第16节）

**被依赖方向（出）**——依赖 CONSOLE-F002 的：
- F-CONSOLE-001 的 CONSOLE-F005（统一控制台 Govern 支柱聚合反馈处理状态）
- CONSOLE-F003（质检/评分中心）间接相关——同一 `EmployeeInstance` 的质量漂移告警（OBS-F007）可以是触发业务人员提交训练反馈的入口，但两者是并列关系，CONSOLE-F002 不消费 CONSOLE-F003 的数据，只是产品体验上可能互相跳转。

架构上的关键约束（本次审计新增，此前文档未写清楚，详见第0/6节）：**CONSOLE-F002 只拥有 `TrainingFeedback` 这一个新实体的事实源，它产出的"变更提案"必须要么落到 AIEMP-F002 的 Instance 覆盖字段（走轻量审核），要么落到 AIEMP-F001 的 Template 变更提案（走 F-APPROVAL-001 + Template Owner 发布流程），CONSOLE-F002 自己不能是任何配置字段的最终事实源，也不能绕过 AIEMP-F001 "不允许扩大平台禁止权限"这条不可变原则。**

## 3｜全球方案调研结果

### 3.1 品类现状（2026年真实存在的技术分层）

"业务人员纠正AI员工行为、形成可追溯变更"这个具体问题在2026年的行业实践里横跨四层，此前任何 Matbox 文档都没有系统梳理过：

1. **人类反馈/标注平台**（Argilla、Label Studio、Scale AI/Surge AI）：解决"人对AI输出打分/纠正，沉淀成结构化数据集"这个通用问题，历史上服务于模型训练数据准备，2026年被广泛用于LLM场景下的"人工审核+反馈收集"。
2. **LLM可观测性平台自带的标注/评分队列**（LangSmith Annotation Queues、Langfuse Annotation Queues）：这层此前已经被 `Matbox_专项03`（F-OBS-001）和 `Matbox_专项05`（F-COST-001）系统性核查过"整体平台替代"不成立，本报告核查这两个平台的**标注队列子功能**单独拿出来是否值得接入，而不是重复核查整体平台。
3. **"AI同事被业务人员纠错"这个具体产品模式的头部参照**：OpenAI Frontier（2026年2月5日发布，四大支柱之一就是"Evaluation and Optimization"反馈闭环）、Sierra（真实客服Agent平台，QA标记→每周走一次模型微调，人工批准后才生效）、Salesforce Agentforce Builder（Agent Script + AI Assistant + 从真实交互生成测试用例）。
4. **完整"数字员工平台"品类的现成实现**：StaffDeck（github.com/OpenBMB/StaffDeck，AGPL-3.0，ModelBest/东北大学-面壁联合实验室/清华THUNLP联合开发）——是本报告调研范围内唯一公开、可读源码、明确针对"AI员工被非技术人员纠错"这个场景做了完整闭环设计的开源项目。
5. **RLHF-as-a-service / 模型厂商官方微调API**：Anthropic、OpenAI、Google 三家现状核查见第0/3.4节，结论是都不适合 Matbox 当前架构。

截至撰写本报告，`docs/技术选型报告/` 目录下**尚未存在** `Matbox_专项00_完整AI员工平台横向调研` 这份文档（已核实目录清单，第9节保留追踪，若后续该报告发布且提出与本报告冲突的结论，需要回来对齐，不是本报告需要现在等待的阻塞项）。

### 3.2 "直接引入一个现成标注/反馈平台"的正面核查（方法论第2条，最重要的问题）

逐一核查 Argilla / Label Studio / LangSmith Annotation Queues / Langfuse Annotation Queues 是否可以让 CONSOLE-F002 放弃自建"反馈捕获+diff映射+审计"整套逻辑，改为引入其中一个：

| 排名 | 方案 | 部署方式 | License/维护状态（2026-09核实） | 能否理解 Matbox EmployeeTemplate/Instance三层Schema | 排名理由 |
|---|---|---|---|---|---|
| **#1** | **Matbox自研**（TrainingFeedback捕获与diff映射，UI交互参考Argilla/Langfuse标注队列设计） | 全部自托管 | 无License问题 | 是（本来就是为此设计） | 唯一理解"纠正 → EmployeeTemplate/Instance具体字段diff → AIEMP-F004审计 → 可能触发Template Owner审批"这条Matbox专属业务闭环的方案；下方所有候选都只解决"收集人类反馈"这一步，不解决"反馈映射到哪个字段、谁能批准"这个核心问题 |
| **#2** | **Argilla**（作为标注队列UI交互模式参考，非代码引入） | 自托管Docker/HF Spaces | Apache-2.0，但**原作者团队已转项目、进入纯bug-fix维护模式，公开寻找新维护者接手**（见6.1节） | 否，且维护状态不允许作为生产依赖 | 概念契合度全场最高（Argilla本来就是为"LLM反馈/RLHF标注"设计），但维护状态是本报告最重要的一条新证据——"有星、有Apache-2.0、有Hugging Face背书"三个传统信号全部正常，唯独"是否还有人在真正维护"这条不正常，恰好验证用户"不是有星就行"的提醒 |
| **#3** | **Label Studio**（作为通用标注UI参考） | 自托管Docker，Community/Enterprise双轨 | Apache-2.0，28.2k star，活跃维护 | 否 | 维护活跃度全场最高，但定位是通用多模态标注工具（图像/视频/音频优先），"多轮审核/共识判定"等最贴近CONSOLE-F002审核场景的能力被锁在付费Enterprise层；且同样不理解Matbox业务Schema，整体引入等于多背一个需要运维的第三方系统换不来核心业务逻辑的减少 |
| 落选 | LangSmith Annotation Queues | 自托管仅Enterprise层，绑定LangChain生态 | 闭源商业SaaS为主 | 否 | 与`Matbox_专项03`已确认的LangSmith否决理由一致（自托管高价门槛+生态绑定），标注队列是其SaaS核心功能的一部分，不能单独低成本拆出来用 |
| 落选 | Langfuse Annotation Queues | 核心开源自托管（重基础设施） | MIT，但`Matbox_专项03/05`已确认Langfuse不作为P0依赖（成本计算bug+防篡改存储缺失） | 否 | 标注队列功能本身真实且体验良好（2026-06-30新增键盘驱动打分），但为了一个标注队列子功能去部署Langfuse整套ClickHouse+Postgres+Redis+S3基础设施不划算，且`专项03/05`已有的结论不应该因为一个子功能被推翻 |

**#1为什么胜过#2/#3**：这不是"没找到候选"，是三个真实候选（Argilla/Label Studio/LangSmith标注队列/Langfuse标注队列，共4个）逐一核查后都不满足"理解Matbox三层Schema+能触发Template审批流程"这两条硬需求。#2 Argilla 概念最贴切，但真实维护状态（原作者已离场、只做bug修复、公开寻找接盘）是本报告核查后发现的实质性新风险，不适合作为生产依赖引入，即使它的Apache-2.0许可证和历史星数都没有问题——这正是用户要求的"不是有星就行，要看真实评价"的具体应用。#3 Label Studio 维护健康但定位错配，且真正贴近本场景的能力在付费层。

### 3.3 完整"数字员工平台"品类核查：StaffDeck（用户特别要求核实的类别，本次审计新增）

用户此前明确要求：不要只在Matbox自己的模块边界内找替代品，还要看有没有现成的、完整的"数字员工平台"产品可以整体参考或采用。StaffDeck 是本报告调研范围内找到的唯一公开、可读源码、明确覆盖"AI员工被业务人员纠错"这个具体场景的开源数字员工平台：

- **产品定位**：面壁智能（ModelBest）联合东北大学-面壁数据智能联合实验室、清华大学THUNLP、OpenBMB、AI9Stars发布，把Agent当"正式员工"管理——发工号、定岗位、做绩效，2026年7月发布（GitHub: `github.com/OpenBMB/StaffDeck`，约1.2k star、200 fork，License为**AGPL-3.0**）。
- **反馈闭环的具体设计（与CONSOLE-F002最直接可比的部分）**："StaffDeck 建立了由全链路 trace、用户反馈、人工兜底组成的反馈迭代机制，记录数字员工的每一句话、每一次API调用，基于用户反馈自动分类，直接向管理者指出SOP修改方向"（腾讯新闻/量子位2026年7月报道交叉印证，属媒体转述厂商表述，非独立第三方评测，本报告如实标注信源性质）。当Agent遇到SOP未覆盖的灰色地带时，不强行给答案，而是保留当前任务状态、请求业务创建者人工介入，由人工把这次经验补充进知识库/SOP，下次遇到类似问题就能直接处理。
- **对 Matbox 的意义**：这个"自动分类反馈 → 指出SOP修改方向 → 人工确认后才真正改" 的三段式，与 CONSOLE-F002 原设计的"反馈进入审核队列 → AIEMP-F004审计确认后才生效"精神高度一致，是一个真实、可核查、当前在被使用的参照架构，验证 Matbox 现有设计方向没有走偏。但 StaffDeck **不能被直接采纳**：(1) License 是 AGPL-3.0，若把它作为对外提供的网络服务组件嵌入会触发源码披露义务，需要按 `Matbox_专项01` 对 TruffleHog 同类条款的处理方式对待（本报告场景不涉及嵌入使用，仅供设计参考，不触发义务）；(2) 它有自己独立的Agent身份/知识库/IM接入体系，与 Matbox 已经建成的 F-AIEMP-001三层模型（Template/Instance/AgentIdentity）+ F-CRED-001+ F-OBS-001完全不是一套系统，整体引入意味着推翻已经Stage 9冻结的架构决策，代价远大于收益。**结论：StaffDeck 的反馈分类三段式流程模式值得学习、不引入代码或依赖。**

这条决定"如果模型厂商真的提供了成熟的、兼容多租户多模型的反馈API，Matbox该不该直接接入而不是自己维护配置层"：

## 7｜源码审查报告

本次审计的核心问题不是"这些工具能不能跑"（Argilla/Label Studio/StaffDeck 三个项目源码都真实存在、可运行，非demo），而是"该不该把它们的代码或运行时引入 Matbox 生产依赖树"，因此本节聚焦决定性事实而非逐行代码审查，与 `Matbox_专项17` 对 Flowable 的处理方式一致：

**关键路线说明（本报告与原设计的实质性差异，非走过场）**：原设计 `Matbox_AI员工管理控制台_正式开发文档_V1.0-RC.md` 只笼统写了"反馈进入审核队列，经AIEMP-F004配置版本审计确认后才实际生效"，本报告核查后要求把这条拆成两条明确路径：(1) `BEHAVIOR_CORRECTION` → 生成对 `EmployeeInstance` 覆盖字段的diff → 校验不超过Template允许边界 → 轻量审核（如Tenant内指定Reviewer确认）→ 直接走AIEMP-F004留痕生效；(2) `POLICY_ADJUST_REQUEST` 或任何会扩大 `forbidden_actions`/`permission_policy` 范围的请求 → 必须生成对 `EmployeeTemplate` 的变更提案 → 强制走 F-APPROVAL-001 正式审批 → 批准后仍要等 Template Owner 按 AIEMP-F001 的版本发布流程实际发布，不能因为F-APPROVAL-001批准了就直接生效，因为Template是跨租户共享资产，单一租户的业务人员反馈不能单方面决定平台级模板的内容。

## 11｜自研、复用、二开和采购的边界

- **OWN（Matbox自己拥有事实源）**：`TrainingFeedback`实体与状态机；反馈分类（Triage）规则；反馈→字段级diff映射逻辑；轻量审核 vs 正式审批的路由判断逻辑。
- **REUSE（引用其他专项的事实源，不复制）**：`EmployeeTemplate`/`EmployeeInstance`（AIEMP-F001/F002，最终字段事实源）；配置版本diff格式与审计存储（AIEMP-F004，RFC 6902 JSON Patch协议本身）；F-APPROVAL-001（policy-level审批状态机，不新建第二套审批引擎）；F-OBS-001（原始被纠正AI输出的证据来源）；F-PROVIDER-001（TC-F002分类若需要LLM辅助，复用既有Provider Router，不直连供应商SDK）；F-TENANT-001（鉴权/多租户隔离模式）。
- **MUST NOT REBUILD（禁止重写的外部成熟能力）**：RFC 6902 JSON Patch标准本身（不自造diff协议，与`专项15`结论一致）；F-APPROVAL-001的审批状态机（不因为这次是"业务人员发起"就自建一套平行审批流程）。
- **参考但不引入代码（本报告新增的第四类边界，介于REUSE和MUST NOT REBUILD之间）**：Argilla的标注队列/评分维度交互设计、Langfuse的键盘驱动标注队列体验、StaffDeck的"自动分类反馈→指出SOP修改方向→人工确认"三段式流程模式——这些不是代码或依赖层面的复用，是产品/交互设计层面值得学习的参照，Stage 10前端施工时应作为设计输入，不是空白发明。

## 16｜鉴权、权限与多租户规范（复用F-TENANT-001既有模式）

1. **人类用户访问**：所有 `/console/training/*` 端点要求 Bearer JWT，租户隔离遵循 `TENANT-F004`"共享表+`tenant_id`字段"模式（`TrainingFeedback`表带`tenant_id`，与 `Matbox_专项15` 对 `EmployeeInstance`/`AiEmployeeConfigAudit` 的处理方式一致）。
2. **角色到端点映射**：`POST /feedback` 任意有权访问该 `EmployeeInstance` 的租户内用户可调用；`PUT /feedback/{feedbackId}/review` 仅 Tenant 内被指定为 Reviewer 角色的用户可调用，且鉴权层强制校验 `reviewer != submittedBy`（禁止自审，与 `F-DQ-010` Suppression 双人审批、`TENANT-F004` break-glass 禁止自批准同一原则）。
3. **跨租户隔离**：`TrainingFeedback.employeeInstanceId` 必须属于当前请求的 `tenantId`，否则按 `TENANT_BOUNDARY_VIOLATION` 处理，不做跨租户可见性例外。
4. **Template级变更提案的特殊权限**：`diffTargetLayer=EMPLOYEE_TEMPLATE` 的反馈，其 F-APPROVAL-001 审批通过后，实际发布动作仍需 Template Owner/PlatformAdmin 权限（复用 `Matbox_专项15` 第16节已定的"发布/停用操作仅PlatformAdmin可执行"规则），CONSOLE-F002 不能因为审批通过就自动发布，必须显式转交 AIEMP-F001 的模板发布流程人工确认。
5. **AI员工自身不能提交训练反馈**：`submittedBy` 必须是人类 `userId`，服务间凭据/AgentIdentity 调用本端点一律拒绝（防止AI员工自我"训练"自己，破坏可追溯性前提）。

## 18｜Webhook、回调及异步任务规范

- **TC-F002分类完成事件**：反馈创建后异步触发分类，完成后通过既有Outbox模式（复用F-QUEUE-001/F-TASK-001 Temporal基础设施）广播`FeedbackTriaged`事件，前端订阅刷新状态，不轮询。
- **F-APPROVAL-001审批结果回调**：`POLICY_ADJUST_REQUEST`类反馈提交审批后，审批状态变更由F-APPROVAL-001通过既有Transactional Outbox机制回调CONSOLE-F002更新`appliedViaApprovalId`关联状态，不新建第二套回调机制（复用`Matbox_专项17`已确定的Outbox Dispatcher）。
- **AIEMP-F004配置版本生效回调**：Instance级diff生效后，AIEMP-F004广播配置变更事件，CONSOLE-F002订阅后回填`appliedViaConfigVersionId`并将`TrainingFeedback.status`置为`APPLIED`，不由CONSOLE-F002自己直接写入AIEMP-F004的表。

## 19｜错误码、重试、超时和降级规范

**完全复用** `Matbox_错误码规范_正式开发文档_V1.0-RC.md` 定义的跨模块错误码：

| 场景 | 错误码 | HTTP | 可重试 |
|---|---|---|---|
| JWT缺失/过期/签名无效 | AUTH_UNAUTHENTICATED | 401 | 否 |
| Reviewer等于提交人尝试自审 | AUTH_FORBIDDEN | 403 | 否 |
| employeeInstanceId所属租户与请求tenantId不一致 | TENANT_BOUNDARY_VIOLATION | 403 | 否 |
| sourceEvidenceRef指向的证据不存在 | RESOURCE_NOT_FOUND | 404 | 否 |
| 幂等键冲突（重复提交同一反馈） | IDEMPOTENCY_CONFLICT | 409 | 否 |
| TC-F002分类调用Provider超时 | PROVIDER_TIMEOUT | 504 | 是（有界，超时后降级为待人工分类） |
| Provider不可用 | PROVIDER_UNAVAILABLE | 503 | 是 |
| 未预期的内部错误 | INTERNAL_ERROR | 500 | 是（有界） |

**降级规范**：TC-F002自动分类失败/超时不阻塞反馈提交本身（fail-open到人工分类，因为这是低风险的辅助功能，不是安全关卡）；但TC-F003越界校验（是否扩大`forbidden_actions`）必须fail-closed——校验器不可用时一律按`EXCEEDS_TEMPLATE_BOUNDARY`最严格路径处理，强制走F-APPROVAL-001，不允许因为校验器故障就放行到轻量审核通道，这是与F-DQ-008/TENANT-F003同一原则的安全关卡，不能因为这次是"业务人员发起"就降低标准。

-- 注：EmployeeTemplate/EmployeeInstance/AiEmployeeConfigAudit表由AIEMP-F001/F002/F004提供，本迁移不重建

## 23｜测试集、Golden Set和验收脚本

- **TC-T001**：提交一条`BEHAVIOR_CORRECTION`反馈，验证自动分类结果、diff生成结果落在`EMPLOYEE_INSTANCE`层，走轻量审核后正确写入AIEMP-F004并回填`appliedViaConfigVersionId`。
- **TC-T002**：提交一条会扩大`forbidden_actions`的反馈（无论`feedbackType`标注是什么），验证`boundaryCheckResult`强制为`EXCEEDS_TEMPLATE_BOUNDARY`且`diffTargetLayer`强制为`EMPLOYEE_TEMPLATE`，即使分类器把它误判为`BEHAVIOR_CORRECTION`也不能绕过（这是第0/6节新增P0规则的直接验收用例）。
- **TC-T003**：Reviewer等于提交人时调用`PUT /feedback/{id}/review`，验证返回`AUTH_FORBIDDEN`。
- **TC-T004**：TriageClassifierAdapter调用Provider超时，验证反馈状态停留在`PENDING_TRIAGE`且不丢失，人工手动指定feedbackType后流程可继续（fail-open降级路径验收）。
- **TC-T005**：BoundaryChecker本身故障/异常，验证系统按fail-closed强制走`EXCEEDS_TEMPLATE_BOUNDARY`路径，不静默放行到轻量审核（fail-closed安全关卡验收，对应第19节降级规范）。
- **TC-T006**：跨租户尝试访问他人`employeeInstanceId`的反馈，验证`TENANT_BOUNDARY_VIOLATION`。
- **Golden Set**：至少覆盖10组"业务人员自然语言反馈 → 期望字段级diff"的人工标注样本对，作为TC-F002/F003回归基线，防止未来分类器/映射逻辑调整时静默劣化（模式参考`Matbox_专项01`F-DQ-013的Challenge Set回归思路）。

## 24｜成本、性能、并发及安全要求

- **成本**：TC-F002分类调用属于低频（每条反馈一次）、短Prompt的LLM调用，走F-PROVIDER-001既有成本追踪（COST-F001），不需要专门预算线，但应标注`feature=CONSOLE-TC`维度供后续成本归因分析。
- **性能**：反馈提交（TC-F001）为同步写操作，P95目标<500ms；分类（TC-F002）为异步操作，允许秒级到十秒级延迟，不阻塞用户提交后的即时反馈。
- **并发**：同一`employeeInstanceId`短时间内多条反馈并发提交时，diff映射逻辑必须按提交时间顺序串行应用（避免两条反馈同时修改同一字段产生冲突覆盖），建议对`employeeInstanceId`维度加轻量分布式锁或使用AIEMP-F004本身的乐观并发版本号机制（若已提供）。
- **安全**：`content`字段（业务人员自由文本输入）在传给TriageClassifierAdapter前需做Prompt注入基础防护（不能让恶意反馈文本诱导分类器把`POLICY_ADJUST_REQUEST`误分类为`BEHAVIOR_CORRECTION`从而绕过审批，第19节已有BoundaryChecker兜底作为最后一道防线，但Triage层也应做合理防护，纵深防御而非单点依赖）。

## 27｜最终验收标准

1. 业务人员能对某个`EmployeeInstance`的具体一次产出提交结构化修正反馈，且反馈必须关联真实存在的`evidenceBundleRef`，不允许凭空提交。
2. 任何试图扩大`forbidden_actions`/`permission_policy`范围的反馈，无论其`feedbackType`标注或分类器判断结果如何，最终必须走`EMPLOYEE_TEMPLATE`层级的F-APPROVAL-001正式审批，不能在`EMPLOYEE_INSTANCE`层被轻量审核直接放行——这是第0/6节新增P0规则，验收时必须显式测试绕过尝试（对应TC-T002）。
3. 反馈生效后，必须能在AIEMP-F004的配置版本审计中查到对应的diff记录和操作人，不允许"悄悄改了但查不到"（沿用原设计验收标准，本报告确认技术路径可实现）。
4. Reviewer不能等于反馈提交人（防止自审自批）。
5. 分类器故障不能导致反馈丢失（fail-open到人工分类），但越界校验故障必须fail-closed到最严格路径（TC-T004/T005验收覆盖）。
6. 未引入Argilla/Label Studio/StaffDeck的代码或运行时依赖（Code Review检查项）。
