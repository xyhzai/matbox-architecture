2026独立复核：这5个工具选型现在还站得住吗（2026-09-03新增，不是转述文档，是这次真去查的）

      

        
SonarQube2026年真实对比：它现在的强项就是"纯代码质量/覆盖率"，安全能力已经不是重点——DQ本来就只让它管代码质量，安全另外交给别的工具，分工是对的

        
OpenGrep2025年1月从Semgrep分叉出来的——因为Semgrep公司把功能收进付费版，一群安全公司联合分叉出最后一版开源代码延续。到2026年初仍在正常维护，规则格式全兼容。选它不是过时，是"不被厂商锁死"

        
Betterleaks老牌工具Gitleaks原作者亲自做的继任者。真实跑分识别率98.6%，比Gitleaks的70.4%高一大截，Gitleaks原作者精力已转移，Betterleaks才是真正在更新的那个

        
Trivy2026年真实对比原话："大多数团队现在的务实推荐——从Trivy开始"

        
OPA最成熟通用的策略引擎，比Kyverno（只能管Kubernetes）、Cedar（只能管权限）覆盖面都广，DQ需要通用判定，选它是对的

      

      
结论：5个选型现在查下来都站得住，不是随便选的。


      
调用方式确认：不是编进Matbox自己代码里的，LGPL风险不适用（2026-09-03当场查已用过的资料解决，不留存疑）

      
SonarQube和OpenGrep用的是LGPL协议——如果把它们的代码静态编译进Matbox自己的程序，会连累Matbox的代码也被迫开源；但如果只是当外部独立程序调用就没事。这个问题不用去查新资料，答案已经在上面卡片⑥"施工面检查"里写过了，只是之前没把它跟License风险连起来看：

      

        
SonarQube入口/Route原文写"Backend adapter；Sonar server internal"——跑在自己的服务器进程里，Matbox只是发请求过去，不是编进代码里

        
OpenGrepProvider行原文写"pinned binary + internal rule pack"——是调用外部二进制文件，不是编进代码里

        
Betterleaks / Trivy / OPAMIT / Apache-2.0协议，本来就没有这层风险；且三个也都是"pinned binary/CLI/container"调用方式，跟上面两个一致

      

      
结论：5个工具全部是外部进程调用（server/binary/CLI），没有一个是静态链接进Matbox自己代码的，LGPL的copyleft风险不适用。这条现在就能确认，不用等Stage10。
